# 产品需求与规划

## 适用场景

- 收到一堆需求需要判断做哪个、先做哪个。
- 写 PRD 让研发能准确理解要做什么。
- 规划版本节奏与路线图。
- 不适用：技术方案设计（用 `gh-architecture-patterns`）；项目排期细节（用 `gh-project-management`）。

## 前置条件

- 明确产品阶段：探索期（验证方向）还是成熟期（优化指标）。阶段不同，判断标准不同。
- 拿到真实用户证据：访谈记录、行为数据、客服工单，而不是"领导说要这个"。

## 步骤

1. **把需求还原成问题**：用户说"要导出按钮"，真问题可能是"我要把数据给老板看"。写清楚**谁、在什么场景、遇到什么阻碍、期望达成什么**。
2. **验证问题真实性**：有没有数据或案例支撑？多大规模用户遇到？不解决会怎样？
3. **优先级排序**：
   - 用 RICE：`(触达 × 影响 × 信心) / 投入`。或
   - 用价值-成本四象限：高价值低成本优先做，低价值高成本直接砍。
   - 排序结果必须能解释"为什么这个排在那个前面"。
4. **PRD 结构**（缺一项研发就得反复问）：
   - 背景与目标（要解决什么问题、成功指标是什么）
   - 用户故事（作为…我要…以便…）
   - 功能详述（主流程、异常流程、边界情况）
   - 验收标准（可判定的断言，不是"体验流畅"）
   - 非功能要求（性能、权限、兼容性）
   - 不做什么（明确排除项，防止范围蔓延）
5. **画流程图**：主路径 + 异常路径（失败、超时、无权限、空数据）。异常路径是最容易被漏掉、上线后最容易出问题的地方。
6. **验收标准写成可测**：如"列表加载超 2 秒显示骨架屏""无结果时显示空状态与引导文案"。
7. **路线图**：按里程碑排，每个里程碑有明确的可交付价值，而不是按功能堆叠。

## 常见坑

- 直接接需求当方案，没还原到真实问题。
- PRD 只写正常流程，异常与边界全靠研发猜。
- 验收标准不可判定（"界面美观""体验流畅"）。
- 优先级按"谁嗓门大"或"谁先提"排。
- 一个版本塞太多功能，每个都做一半，无法验证价值。
- 没有明确的"不做什么"，范围持续蔓延导致延期。
- 成功指标缺失，上线后无法判断是否成功。

## 验证

- 每个需求能追溯到用户问题与证据。
- PRD 的验收标准逐条可判定。
- 异常路径全部列出。
- 优先级排序有可复述的理由。
- 明确写出本期不做的范围。
