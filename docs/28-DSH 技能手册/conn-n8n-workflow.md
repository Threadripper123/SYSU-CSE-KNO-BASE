# n8n 工作流连接器

## 适用场景

- 要在 n8n 里搭数据同步、Webhook 接收、定时报表、多系统串联。
- 已有工作流报错需要定位：表达式求值为空、节点拿不到上游字段、无限重试。
- 不适用：本机的一次性脚本（用 `gh-automation-workflow`）。

## 前置条件

- n8n 实例地址与 API Key 已就绪（自托管就是 localhost:5678）。
- 明确触发方式与数据形状，先拿到一条真实样例数据再设计节点。

## 步骤

1. **先定数据契约**：把输入 JSON 的一个真实样例贴出来，标注哪些字段必需、哪些可能缺失。
2. 节点结构从"输入 → 变换 → 输出"三段搭，中间用 Set/Code 节点做形状归一，避免每个节点各猜字段。
3. 表达式写法：
   - 引用上游：`{{ $json.field }}`；跨节点引用用 `{{ $('Node Name').item.json.field }}`。
   - 可选字段给默认值：`{{ $json.x ?? 'default' }}`。
   - 时间字段显式时区，避免容器默认 UTC 导致日期偏一天。
4. 批处理：用 Split In Batches 控制 API 压力；HTTP 节点设置超时与重试（开启 Retry On Fail，退避次数写死）。
5. 错误处理：给关键节点接 Error Trigger 或 `continueOnFail`，并把失败项落到独立分支汇总后统一通知，而不是整条流程中断。
6. 子流程：重复逻辑抽成 Sub-workflow 并用 Execute Workflow 调用，参数通过显式输入传递。
7. **测试顺序**：单节点执行 → 关闭下游逐个验证 → 全流程跑一次 → 用异常数据跑一次。

## 常见坑

- 表达式写 `{{ $json }}` 返回整对象，下游节点引用字段时全空；必须精确到属性。
- Webhook 节点默认响应模式是"收到即回"，异步处理失败用户看不到；需要同步结果时改 Respond to Webhook。
- 循环里调用外部 API 不限速被封；用 Split In Batches + Wait。
- 凭据直接写在节点 JSON 里导出会泄露，导入导出要在界面上重新绑凭据。
- 版本升级后节点参数结构变化，导出再导入可能丢配置，升级前备份工作流 JSON。

## 验证

- 用一条真实数据和一条边界数据（空数组/缺字段）各跑通一次。
- 失败分支实际触发一次，确认通知与落库生效。
- 导出工作流 JSON 存档，记录版本。
