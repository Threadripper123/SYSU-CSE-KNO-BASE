# 项目管理与交付排期

## 适用场景

- 新项目启动需要 WBS 拆解与排期。
- 项目已延期，需要定位瓶颈与重排计划。
- 多方协作，需要明确依赖、接口人与交付节点。
- 不适用：单人一次性小任务（直接做即可）。

## 前置条件

- 先明确四要素：范围、时间、成本、质量。**四者只能保三个**，必须问清哪个可以牺牲。
- 拿到真实的人力投入（人天），而不是"大概两周"。

## 步骤

1. **WBS 拆解**：拆到"一个人 1–3 天能完成、有明确完成标准"的粒度。粒度太粗无法估，太细管理成本过高。
2. **工期估算**：三点估算 `(乐观 + 4×最可能 + 悲观) / 6`，并单独列出"不确定性最大的三项"。
3. **依赖梳理**：画前置关系，找出关键路径。关键路径上任一任务延期直接导致项目延期——资源优先保这里。
4. **排期**：给关键路径留缓冲（建议为关键路径总时长的 15%–25%），不把缓冲均摊到每个任务（会被逐项蚕食）。
5. **风险登记**：每条风险写"触发信号 + 影响 + 应对 + 责任人"。只写"可能有风险"没有意义。
6. **跟踪机制**：固定节奏（如每周）更新完成度、阻塞项、变更请求。用"已完成/进行中/阻塞"而非百分比自评。
7. **变更控制**：范围变更必须显式记录，并说明代价（延期多久 / 砍掉什么）。

## 常见坑

- 100% 排满无缓冲，任何小意外都导致全线延期。
- 只估开发不估评审、联调、测试、部署与返工，这些常占总工时 40% 以上。
- 依赖外部团队却没有约定交付日期与升级路径。
- 用"进度 90%"自评，实际剩余工作比前 90% 还多（长尾任务）。
- 多人并行任务没有明确接口人与交接物，出现"以为对方在做"。
- 里程碑只对内部，对外承诺的日期没有留足风险余量。

## 验证

- 每个任务的完成标准可判定（不是"基本完成"）。
- 关键路径与缓冲明确写出。
- 风险登记表每条有责任人与应对动作。
- 排期可追溯到人天估算。
