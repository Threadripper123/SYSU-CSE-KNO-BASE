# MCP 服务端连接器

## 适用场景

- 把一个外部 API、内部系统或本地 CLI 封装成 agent 可调用的工具集。
- 已有 MCP server 行为不理想（工具太碎、命名混乱、报错不可读）需要重构。
- 不适用：只需要一次性调用某个 HTTP 接口（直接写脚本更快）。

## 前置条件

- 先确认协议与传输方式：stdio 适合本机进程，HTTP/SSE 适合远程。
- 选定语言：Python 用 FastMCP，Node/TypeScript 用官方 SDK。项目已有主语言优先。
- 不要假定客户端支持动态工具发现以外的能力（资源、提示词），核心能力必须由工具承载。

## 步骤

1. **先做接口调研再写代码**：列出目标系统全部端点与鉴权方式，写成表格；标出哪些需要组合才能完成任务。
2. **工具划分**：底层端点覆盖与高层工作流工具要平衡。优先覆盖全，但为高频组合提供一次调用完成的工作流工具。
3. **命名与描述**：工具名统一前缀与动词（`github_list_prs`、`github_create_issue`），描述写清「什么时候该用」而不是「它做什么」。
4. **参数与返回**：参数用窄类型与枚举，必填项尽量少；返回结构化 JSON，错误用明确的错误码与可操作提示，不要抛裸异常字符串。
5. **鉴权**：token 从环境变量读取，永不写进代码或日志；缺 token 时给出清晰的配置指引而不是崩溃。
6. **本地自测**：写一个最小的调用脚本走通每个工具，验证正常与失败两条路径。
7. **注册**：在 DSH/客户端配置里登记 server 命令与参数；随后确认工具真的出现在工具列表里。

## 常见坑

- 工具粒度过细（一个工具只做一次字段读取）会让 agent 大量往返；过度合并又让参数复杂。原则：一个工具完成一个有意义的动作。
- 描述里写实现细节，模型看不懂该在什么时候调用它。
- 用 print 输出调试信息污染 stdio 传输协议——stdio 模式下 stdout 必须只承载协议帧，日志一律走 stderr。
- 大返回不分页，直接把上下文撑爆；列表类工具必须支持 limit/offset 并返回总数。
- 密钥写死在示例里被复制进仓库。

## 验证

- 每个工具都有一条可复现的成功调用与一条失败调用记录。
- 断开被集成服务时，工具返回可读错误而不是进程崩溃。
- 客户端重启后工具列表正确加载。
