# 数据管道与 ETL

## 适用场景

- 多源数据汇总到一个库/文件，需要定时更新。
- 数据脏乱：重复、缺失、格式不一，需要清洗规则。
- 已有管道经常失败或数据对不上。
- 不适用：单次数据分析（用 `gh-numerical-computing`）；纯脚本编排（用 `gh-automation-workflow`）。

## 前置条件

- 明确数据源（库表/API/文件）、目标（库表/数仓/文件）、更新频率与延迟要求。
- 明确数据量与增长：决定用全量覆盖还是增量同步。
- 明确一致性要求：允许多大延迟，是否需要事务。

## 步骤

1. **分层**：原始层（原样落地，不做转换）→ 清洗层（标准化、去重、类型转换）→ 应用层（聚合、宽表）。**原始层必须保留**，出问题才能回溯。
2. **抽取**：
   - 全量：小表直接覆盖，简单可靠。
   - 增量：用更新时间戳或自增 id 水位线（watermark），水位线存独立的元数据表，成功后更新。
   - API 源：分页 + 限速 + 断点续传。
3. **清洗规则显式化**：每条规则写成可测试的函数并配单测——空值填充策略、类型转换失败处理、去重主键定义、异常值范围。
4. **数据质量校验放在入库前**：
   - 行数波动（对比上期 ±50% 报警）。
   - 主键唯一性。
   - 非空率、枚举值合法性。
   - 关键指标环比突变。
   校验失败应阻断入库而不是写坏数据。
5. **幂等写入**：按分区/主键覆盖（`DELETE + INSERT` 同事务 或 upsert），重跑不产生重复。
6. **调度与监控**：任务成功/失败/耗时写日志；失败自动重试并告警；记录每次运行的行数与耗时便于发现退化。
7. **文档化血缘**：每个目标表标注来源、转换逻辑、更新频率、负责人。

## 常见坑

- 增量同步用"当前时间"做水位线，漏掉事务提交晚的数据；应用源端数据的业务时间而非处理时间。
- 全量重跑没做幂等，数据翻倍。
- 清洗规则写在代码各处，改一处忘一处，导致口径不一致。
- 上游改字段类型或改名，管道静默写入 NULL，几天后才发现。
- 只用行数判断成功，没做内容校验。
- 时区不统一（源是 UTC、目标是本地时区），跨日数据错位。
- 大表一次性加载进内存 OOM；应分块（`chunksize`）。

## 验证

- 重跑同一批次两次，结果完全一致（幂等实测）。
- 注入一条脏数据，确认被校验拦截并告警。
- 上游字段缺失时管道明确失败而非静默通过。
- 记录并报告每步行数与耗时。
