# 代码审查与质量门禁

## 适用场景

- 用户要求审查 PR、review 代码、把关合并、找出改动风险。
- 提交前自查：确认本次改动是否引入回归、竞态或兼容问题。
- 不适用：纯格式整理、单纯跑测试（用 `gh-testing-strategy`）。

## 前置条件

- 能读到 diff（`git diff`、`git log -p`）与相关文件全文。
- 明确审查范围：某个 PR、某次提交范围，还是工作区未提交改动。
- 不假定远程 CI 可用；本地无法执行时说明限制，不要编造测试结果。

## 步骤

1. 先定范围与意图：读 PR 描述/提交信息，写出「这次改动想达成什么」。意图不明的先问，不要猜。
2. 圈定受影响面：用 `git diff --stat` 找热点文件，再用 grep 追调用方（谁依赖被改的签名/行为）。
3. 分层审查，按风险从高到低：
   - **正确性**：边界条件、空值、并发、错误分支是否被吞掉。
   - **安全**：输入校验、鉴权、SQL/命令拼接、密钥是否外泄、日志是否脱敏。
   - **兼容性**：对外接口/数据格式/配置项是否有破坏性变更，是否需要迁移脚本。
   - **性能**：循环内 I/O、N+1 查询、无界内存增长。
   - **可维护性**：命名、重复逻辑、测试是否覆盖新增分支。
4. 每条意见写成「位置 + 问题 + 为什么是问题 + 建议改法」，按 阻塞/建议/疑问 三档标注。
5. 给结论：可以合并、改后合并、或需要重做，并列出放行前必须解决的条目编号。
6. 交付前自检：是否有意见只是风格偏好却说成缺陷；是否漏掉未改动的调用方。

## 常见坑

- 只看 diff 不看上下文，把「原本就这样」的问题算成这次改动引入的。用 `git log -L` 或 blame 确认问题归属。
- 把「能跑」当作「正确」：失败分支、空集合、并发重入往往没被任何测试覆盖。
- 意见堆成清单没有优先级，作者无从下手；必须标阻塞项。
- 审查大 diff 时逐行读完再下结论，中途记住的细节会失真——分块审查并即时记录。

## 验证

- 每条阻塞项都能指出具体文件与行为差异。
- 结论与意见一致（存在未解决阻塞项就不能写「可以合并」）。
- 若声称某处有测试覆盖，必须给出测试文件与用例名。

## 参考

- 与 `gh-api-design`（对接口改动）、`gh-sql-optimization`（对查询改动）配合使用。
- 与 `gh-testing-strategy` 交叉：新增分支是否有对应测试。
