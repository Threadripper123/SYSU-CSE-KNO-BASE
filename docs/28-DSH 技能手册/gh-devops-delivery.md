# 构建部署与交付

## 适用场景

- 要写 Dockerfile / compose / CI 流水线（GitHub Actions 等），或决定发布策略。
- 线上故障需要复盘：确认发布环节是否引入变更、如何回滚。
- 不适用：单机本地脚本跑起来即可的场景。

## 前置条件

- 先读项目现有构建脚本与 .github/workflows，沿用既有约定，不要另造一套。
- 确认目标平台（本机 Windows、Linux 服务器、内网），镜像源与网络可达性先探测。

## 步骤

1. 明确交付物：是二进制、镜像、静态产物还是安装包；谁消费它。
2. 构建可复现：锁定依赖版本、固定基础镜像 tag（不用 latest）、构建参数显式化。
3. 镜像分层：先 COPY 依赖清单装依赖，再 COPY 源码，让缓存真正生效；多阶段构建剥离编译工具链。
4. 配置外置：密钥走环境变量或密钥管理，不进镜像；提供 .env.example。
5. 发布策略：蓝绿、滚动或金丝雀任选其一并写清判定标准（错误率、延迟阈值），必须同时写回滚步骤与触发条件。
6. 可观测性：健康检查端点、结构化日志、关键指标与告警阈值；日志脱敏后再出。
7. 交付时列出：一次完整发布的命令序列、验证点、回滚命令。

## 常见坑

- 本机 maven/npm 直连官方源超时：改用内网或云厂商镜像（如腾讯/阿里镜像），并在配置里固定下来。
- CI 里能跑本机不能跑：多半是路径分隔符、大小写、行尾符或时区差异。
- 容器内时钟/时区/编码默认值是 UTC 与 POSIX，中文输出变问号。
- 只写「如何发布」不写「如何回滚」，出事时无路可退。
- 打包产物与源码目录同盘同步（如网盘同步目录）会被长时间占用锁文件，交付物应放独立目录。

## 验证

- 在干净环境（新容器/新机器）按文档执行一次构建，能复现出同样产物。
- 回滚命令在测试环境实际执行成功。
- 健康检查端点返回真实依赖状态，不是硬编码 200。
