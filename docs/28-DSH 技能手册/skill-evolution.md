# 技能自进化

## 何时使用

- 完成了一个多步骤任务，过程中有非显而易见的排错、工具用法或流程。
- 用户纠正了你的做法，或你加载的 skill 内容不准确、缺失、过时。
- 同一类任务第二次出现，而现有 skill 覆盖不足。
- 不适用：纯查询、一次性操作、结果未验证、用户明确说不要沉淀。

## 核心原则

1. 先查再写：先列出 DSH 技能目录与项目 `.dsh/skills`，读相关 SKILL.md 的 frontmatter，确认没有可更新的技能。DSH 技能目录是 `$DSH_HOME/skills`；未设置 `DSH_HOME` 时，Windows 默认 `%USERPROFILE%\.dsh\skills`，其他平台默认 `~/.dsh/skills`。
2. 优先更新，其次新建；能合并就不新增。
3. 只写已验证的事实：命令、路径、参数、坑、验证方法。不要写猜测。
4. 少而精：一个技能解决一类任务；正文控制在 200 行内，长资料放 `references/`。
5. 不写入密钥、token、个人隐私、客户数据、一次性日志。
6. 每个任务最多新建 1 个技能；同类技能超过 3 个时，先提议合并。

## 决策

- 已有技能覆盖 ≥70%：更新它。
- 只有部分重合：优先扩展现有技能的“变体/边界”章节；确实不同再新建。
- 没有可复用内容：不写，只在答复中说明。
- 不确定是否值得：先放到项目 `.dsh/skills` 观察，稳定后再提升为全局。

## 新建流程

1. 选名：kebab-case，动词或领域名，如 `pdf-table-extract`；不要与现有或内置技能重名。
2. 选位置：跨项目 → `$DSH_HOME/skills/<name>/SKILL.md`；项目专用 → `<项目根>/.dsh/skills/<name>/SKILL.md`。写入时使用解析后的绝对路径，不要依赖 shell 的 `~` 展开。
3. 写 frontmatter：`name` 与目录名一致；`description` ≤500 字符，写清“做什么 + 何时用”，不要写“这是一个技能”。
4. 正文模板：
   - `# 标题`
   - `## 适用场景`（触发条件与不适用）
   - `## 前置条件`（工具、权限、输入）
   - `## 步骤`（编号、可复制命令、每步验证点）
   - `## 常见坑`（来自本次任务的真实错误与修复）
   - `## 验证`（如何确认成功）
   - `## 参考`（可选，指向 references/ 或 URL）
5. 写入后重新读取文件，检查 frontmatter 能被解析、名称合法、正文非空；目录中不要放多余的根级 `.md` 文件（会被当成技能）。
6. 在最终答复中报告路径与一句原因。

## 更新流程（进化）

1. 读取当前 SKILL.md 全文，保留仍然正确的部分。
2. 最小改动：补充缺失步骤、修正错误命令、更新边界条件；不要整篇重写。
3. 如果“何时使用”发生变化，更新 `description`（目录会刷新）；只改正文不会刷新目录，但下次加载会读到新内容。
4. 在正文末尾维护 `## 变更记录`：
   `- YYYY-MM-DD: 一句话说明改了什么、为什么（来自哪次任务/纠正）。`
5. 重新读取并校验；在答复中说明更新点。

## 质量门槛（不满足就不要写）

- 一个不了解背景的 agent 能按步骤复现。
- 至少包含一条本次任务中真实踩过的坑或非显而易见的细节。
- 没有未经验证的断言；没有秘密与隐私。
- 描述能让人或模型判断“何时该加载”。
- 与现有技能不重复；重复则合并。

## 安全与边界

- 写 `$DSH_HOME/skills` 需要文件权限；若被沙箱拒绝，改用项目 `.dsh/skills`（通常在工作区内），或向用户说明，不要绕过沙箱。
- 不修改 bundled 技能（`gh-*`、`office`、`univer` 等）；如需调整，先确认优先级与影响。
- 不执行技能中未验证的破坏性命令；不自动安装依赖。
- 技能是给未来 agent 的指令，不是聊天记录；不要粘贴大段对话。

## 自检

- [ ] 名称 kebab-case 且唯一
- [ ] description 说明“做什么 + 何时用”
- [ ] 步骤可复现，含验证点
- [ ] 记录了真实坑点
- [ ] 无秘密、隐私、一次性内容
- [ ] 已更新而不是重复新建
- [ ] 已在答复中报告路径
