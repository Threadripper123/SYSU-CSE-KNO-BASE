# 安全审查与加固

## 适用场景

- 上线前做安全检查；审查第三方代码或配置。
- 排查疑似漏洞（越权、注入、信息泄露）。
- 制定密钥管理与最小权限方案。
- 不适用：代码质量与可维护性（用 `gh-code-review`）。

## 前置条件

- 明确系统边界：谁可以访问、数据敏感等级、是否暴露公网。
- 拿到真实配置与依赖清单，不要只读代码不看部署配置。

## 步骤

1. **先查三类最常见问题**：
   - **注入**：SQL 拼接（应全用参数化查询）、命令拼接（`shell=True` + 用户输入）、模板注入、路径拼接（`../` 穿越）。
   - **鉴权**：每个接口是否都校验了身份与权限；是否存在水平越权（改 id 就能看别人数据）；管理接口是否与业务接口共用认证。
   - **密钥**：代码/配置/日志/前端包里是否有明文密钥；是否可用低权限替代。
2. **输入校验**：所有外部输入（HTTP、文件、环境变量、第三方回调）都要校验类型、范围与长度；白名单优于黑名单。
3. **敏感数据**：传输用 TLS；存储中密码用 bcrypt/argon2 加盐哈希；日志中脱敏（手机号、身份证、token 打码）。
4. **依赖安全**：`pip-audit` / `npm audit` 查已知漏洞；锁定版本并定期更新。
5. **配置加固**：默认口令必须改、调试模式关闭、错误信息不暴露堆栈与路径、CORS 不用 `*`、上传限制类型与大小。
6. **文件与权限**：上传文件重命名并存储在 web 根目录外、禁止执行；服务以最小权限账号运行。
7. **输出**：按风险等级（严重/高/中/低）列出问题、利用条件、修复方案与验证方法。

## 常见坑

- 只在代码里找漏洞，忽略反向代理、容器配置、默认口令等部署层问题。
- 用了 ORM 就以为没有注入，仍在用字符串拼接 `where` 条件。
- 鉴权放在前端或只在前端隐藏按钮。
- 密钥放在代码里"以后删"，结果进了 git 历史。
- 依赖漏洞扫描报了一堆，但不评估实际可达性，全部当作必须修。
- 报错页面暴露堆栈、SQL、绝对路径。
- 权限"临时"放大后忘记收回。

## 验证

- 每个结论对应具体文件与行号，给出可利用路径（不能利用的要说明为何不能）。
- 修复后重新验证：越权接口返回 403、注入 payload 无效、日志中密钥已打码。
- 明确残留风险与接受理由。

## 参考

- 与 `gh-code-review`（质量维度）、`gh-devops-delivery`（部署加固）配合。
- 涉及真实生产系统时，只做防御性评估，不在未授权环境下测试攻击。
