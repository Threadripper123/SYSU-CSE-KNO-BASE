# 测试策略与自动化

## 适用场景

- 新功能需要补测试，或用户问「这个改动要写哪些测试」。
- 已有测试失败需要定位，或需要判断覆盖率是否足够。
- 不适用：单纯审查代码（用 `gh-code-review`）。

## 前置条件

- 先摸清项目既有测试框架与命令（读 package.json scripts / pytest 配置 / Makefile），不要另起一套。
- 确认能跑测试；跑不起来的先修环境，不要跳过验证就宣称通过。

## 步骤

1. 分层布置，不要把所有东西都塞进端到端：
   - **单元**：纯函数、解析、校验、状态机。快、无外部依赖。
   - **集成**：数据库、文件系统、HTTP 边界。用真实或内存实现，别全 mock 成空壳。
   - **端到端**：关键用户路径，数量克制，只覆盖不可替代的场景。
2. 从改动反向推测试：每个新增分支至少 1 条用例；每个修复的 bug 先写复现用例（红）再修（绿）。
3. 边界优先：空集合、单元素、最大长度、超时、并发重入、错误返回码。
4. 断言要具体：断言值与结构，不要只断言「不抛异常」或「返回非空」。
5. 稳定性：去掉依赖时间/随机/网络的脆弱用例，必要时注入时钟与随机种子。
6. 跑完给出结果：通过数/失败数、失败用例的完整报错、覆盖到的分支；不要用「大致通过」这类表述。

## 常见坑

- 全 mock 的集成测试通过但真实链路失败：至少保留一条打通 shell 的用例。
- flaky 用例反复重跑掩盖问题：先定位不稳定根因（时序、共享状态），不要加重试掩盖。
- 覆盖率当作目标：只追数字会写无断言的空测试；看未覆盖分支是否有意义。
- Windows 上路径分隔符、大小写、换行符差异导致测试在 Linux 过、本机挂。

## 验证

- 失败用例必须能给出复现命令与完整堆栈。
- 声称「已覆盖」需列出测试文件与用例名。
- 修改测试后重跑全量，确认没有连带失败。
