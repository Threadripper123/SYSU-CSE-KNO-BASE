# SYS-03 操作系统与云原生 2025–2026：Linux 6.x、eBPF、io_uring、Kubernetes 1.34、Wasm

> 资料截至 2026-11-15；覆盖 2023-11 至 2026-11，重点 2024–2026。

**一句话结论**：2026 年内核最显眼的事件是版本号从 6.x 跳到 7.x（7.0 于 2026-04-12 发布），但真正改变云原生底座的是几件「不起眼」的事——`open_tree(2)` 与 `clone3(2)` 的新 flag 让容器创建更快、`sched_ext` 有了子调度器并按 cgroup 分配、io_uring 拿到 BTF 与过滤能力；Kubernetes 这边则把「资源可分配、状态可观测」的能力（DRA、User Namespaces、PSI、原生直方图）陆续推成 GA 或 Beta。

标题里的「Linux 6.x」「Kubernetes 1.34」都是 2025 年基线。到 2026-11-15，内核主线已经到 7.4-rc2，Kubernetes 到 1.37。本文按真实状态写，标题保持任务分配原样。

## Linux 7.0：一次主版本号跃迁

Linux 7.0 于 2026-04-12 发布。按 kernelnewbies 的汇总，这一版的要点是：文件 I/O 错误上报的新 API；XFS 的健康监控；对 Clang 静态分析的支持；io_uring 对 filter 的支持更好；`open_tree(2)` 新增 flag，让容器 setup 更快更简单；交换（swap）性能改善；`rseq(2)` 的时间片扩展机制；抢占选择的简化；AccECN 默认开启；Btrfs 的实验性 remap tree。

对云原生最有直接意义的是 `open_tree(2)` 那条：容器运行时构造 mount namespace 时的系统调用序列可以更短，减少启动路径上的内核往返。这类改动不会出现在 benchmark 头条里，但它作用在每一次 Pod 启动上。

## 7.1–7.3：调度器、内存与沙箱

- **7.1（2026-06-14）**：全新的 NTFS 实现；交换实现改进；socket 支持 `user.*` 扩展属性；在支持的硬件上启用 Intel FRED；BTF-powered io_uring；`sched_ext` 支持子调度器；`clone3(2)` 新增 flag 以改善基于 pidfd 的进程管理。
- **7.2（2026-08-16）**：任务调度器变得更 cache-aware，能把共享数据的任务放进同一个 LLC 域；更公平的 GPU 调度；内存回收改进；更精简的交换实现；USB4STREAM；新增 `dm-inlinecrypt` 块设备内联加密target；`openat(2)` 新增 flag；`/proc` 读取加速。
- **7.3**：改善低端 GPU 的 VRAM 管理（游戏场景明显）；完成「按单个 cgroup 分配 BPF 任务调度器」的能力；btrfs 与 ext4 性能改进；新的 `failfs` 伪文件系统加 `fchroot(2)` 系统调用组成的沙箱技术；块设备支持 `RWF_DONTCACHE` 作为 Direct I/O 的替代。

7.3 的更新时间线需谨慎：kernelnewbies 的 7.3 页面最后更新于 2026-10-11，而 kernel.org 的 stable 已到 7.3.4（2026-11-10）。**7.3 的准确首发日期本文未直接读到**，按 stable 分支节奏推断在 2026 年 9 月下旬到 10 月初之间。

| 内核能力 | 版本 | 对云原生的意义 | 采用前提 |
| --- | --- | --- | --- |
| `open_tree(2)` 新 flag | 7.0 | 容器创建路径更短 | 运行时需适配新 flag |
| BTF-powered io_uring | 7.1 | 异步 I/O 的类型信息更完整，eBPF 侧可观测 | 工具链需支持 BTF |
| `sched_ext` 子调度器 | 7.1 | 自定义调度策略可分层组合 | 内核需启用 sched_ext |
| cache-aware 调度 | 7.2 | 多租户混部时减少 LLC 抖动 | 需实测，默认策略不一定最优 |
| 按 cgroup 的 BPF 调度器 | 7.3 | 可按租户/业务定制调度 | 需要 cgroup v2 |
| `failfs` + `fchroot(2)` | 7.3 | 更强的沙箱边界 | 生态工具尚未普及 |

## eBPF 与 io_uring：内核可编程化的两条主线

eBPF 在 2026 年的关键变化不在「能不能挂探针」，而在「能不能安全地替换调度决策」。`sched_ext` 从 6.12 进入主线，7.1 引入子调度器、7.3 完成按 cgroup 分配，意味着一个集群可以给在线业务和批处理业务配不同的 BPF 调度器。这条路的风险也很清楚：调度器是内核最热的路径，任何 BPF 程序的抖动都会放大成全局延迟，生产上必须配合压力测试与快速回滚（停用该 cgroup 的调度器即可，不必重启内核）。

io_uring 的演进方向是把「异步」做得更像普通系统调用：7.0 完善 filter，7.1 引入 BTF 支撑。对用户态运行时（数据库、代理、存储引擎）而言，收益来自减少上下文切换；对运维而言，需要关注内核版本与库版本的匹配，因为 io_uring 的功能探测比传统 syscall 更细碎。

## Kubernetes 1.37：把资源讲清楚

Kubernetes 只维护最近三个 minor 分支，1.19 之后每个 minor 约有 1 年补丁支持。截至 2026-11-15 的支持矩阵是：

| 版本 | 最新补丁 | 补丁日期 | EOL |
| --- | --- | --- | --- |
| 1.37 | 1.37.1 | 2026-09-15 | 2027-10-28 |
| 1.36 | 1.36.5 | 2026-09-15 | 2027-06-28 |
| 1.35 | 1.35.9 | 2026-09-15 | 2027-02-28 |
| 1.34 | 1.34.12 | 2026-09-15 | 2026-10-27（已 EOL） |

1.37 的代号是 Garhwal，发布周期在 2026-05-18 启动。按官方博客的标题看，这一版的重点是把「资源」这件事说清楚：

- Native Histograms 进入 Beta，指标精度与存储成本的权衡有了新选项。
- 新增 Node Lifecycle Conditions，节点状态不再只靠 `Ready` 一个布尔量。
- `KubeletInUserNamespace`（rootless 模式）进入 Beta。
- 支持把工作负载用 HorizontalPodAutoscaler 缩到 0。
- Storage Version Migration 默认启用。
- Metrics API 转正；Pod 级资源管理器、Memory QoS 进入 Beta；In-Place Pod Resize 的抢占支持仍是 Alpha。

1.36 则把几件「底座」事做完了：PSI 指标 GA、声明式校验（Declarative Validation）GA、User Namespaces GA；DRA（动态资源分配）增加更多驱动；同时移除了 Service 的 `ExternalIPs`。这两版连起来看，方向是「把资源分配与状态观测标准化，把历史遗留字段清掉」。

## Wasm：从模块到组件

WASI 现在是三档：0.1（Legacy，POSIX 风格的模块 API）、0.2（Component Model 基础，WIT 接口与跨语言组合；2024 年 1 月底发布）、0.3（**当前稳定版**）。0.3 的核心是把原生 async 加进 Component Model，接口改用 `async func`、`stream<T>`、`future<T>` 表达。落地情况并不齐：Wasmtime 46 及以后默认能跑 0.3 组件，Rust 有 `wasip3` crate，jco 提供面向 Node.js 的实验性 0.3 shim，但多数工具链仍以 0.2 为目标。

对平台团队来说，Wasm 的可用姿势是「插件与策略扩展」而不是「替换容器」：组件模型解决的是跨语言组合与沙箱边界，不是进程隔离与镜像分发。0.3 支持不完整时，从 0.2 起步不会堵死升级路径——支持 0.3 的运行时同时能跑 0.2 组件。

## 调度与可观测：两处最值得先试点

如果只能选两个方向做试点，建议是「调度」与「指标」。

调度侧，`sched_ext` 提供了不用改内核就能替换调度策略的接口，而 7.1 的子调度器让它能分层：基础策略仍由内核负责，业务差异以子调度器叠加。适合的负载是延迟敏感型服务与批处理混部——把批处理的吞吐优化交给一个 BPF 调度器，在线服务仍走默认策略。风险是调度器代码跑在内核热路径上，出问题时表现为全局抖动而不是单点异常，所以试点必须限定在独立节点池，并提前写好「停用该 cgroup 调度器」的回滚步骤。

指标侧，Kubernetes 1.36 让 PSI 指标 GA、1.37 让 Native Histograms 进入 Beta，两件事指向同一个目标：把「资源争抢」从经验判断变成可量化信号。PSI 给出的是任务在 CPU、内存、IO 上的停顿时间占比，比 load average 更贴近真实体验；原生直方图则让分位数查询不再依赖预先设定的桶。两者一起用，可以把「节点是不是不够」这类争论变成可复现的数据。

## 升级的现实路径

从 6.x 走到 7.x，工程上通常分三步，而不是一次性跳版本：

1. **先对齐 longterm**：把生产节点统一到 6.12 或 6.18 的最新补丁，确认已知 CVE 已修。这一步不改特性，只降风险。
2. **再验证容器运行时与存储驱动**：`open_tree(2)`、`clone3(2)`、io_uring 的行为变化最先被 runc/containerd 与 CSI 驱动感知。做法是在预发集群用同一份工作负载跑一遍 Pod 启动耗时与挂载成功率。
3. **最后才评估新特性**：`sched_ext`、`failfs`、`RWF_DONTCACHE` 这类能力应当以「独立节点池 + 可回滚」的方式引入，而不是随内核升级一起打开。

Kubernetes 侧的顺序相反：先升控制面再升 kubelet 是标准做法，但要注意 1.34 已 EOL——如果集群还在 1.34，升级不是「计划内维护」而是「补安全债」，应优先排期。升到 1.36/1.37 时，重点验证的是 User Namespaces（1.36 GA）与 rootless kubelet（1.37 Beta）对现有安全策略的影响。

## 云原生底座的三个硬约束

- **cgroup v2 是前提，不是选项**：按 cgroup 分配 BPF 调度器（7.3）、Memory QoS（1.37 Beta）、PSI 指标（1.36 GA）都建立在 cgroup v2 之上。仍在 cgroup v1 的节点，这些能力要么不可用，要么语义不完整。
- **上游能力到发行版有 6–18 个月时差**：kernel.org 的 7.3 不代表你的节点能跑 7.3 的特性，企业发行版通常把特性回移到 5.14/6.6 这类基线。判断「能不能用」要看发行版文档的 backport 列表。
- **Wasm 是补充层而非替换层**：组件模型解决的是跨语言组合与沙箱，不解决镜像分发、网络与存储编排。把它放进「插件/策略扩展」的位置，比放进「替代容器」的位置更符合当前成熟度。

## 常见坑与局限

- **把 stable 当 LTS**：7.3.4 只保证当前稳定线的短期维护；长期生产应对齐 6.12 或 6.18。
- **忽略已 EOL 的版本**：7.2（EOL 2026-11-01）与 Kubernetes 1.34（EOL 2026-10-27）都不再收修复。
- **发行版内核 ≠ 上游内核**：RHEL/Ubuntu 会把特性回移到旧版本号上，判断能力时看的是发行版 backport 列表，不是 `uname -r` 的主版本号。
- **rootless kubelet 仍是 Beta**：`KubeletInUserNamespace` 在 1.37 才 Beta，生产采用要评估特权端口、cgroup 委派等限制。
- **Wasm 的版本碎片**：0.1/0.2/0.3 并存，选运行时前先确认它支持哪一档，而不是看「支持 WASI」四个字。
- **BPF 调度器的回滚路径**：自定义调度器出问题时的止损动作是停用对应 cgroup 的调度器，预案要提前写好。
