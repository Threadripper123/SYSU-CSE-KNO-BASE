> 资料截至 2026-11-15；覆盖 2023-11 至 2026-11，重点 2024–2026。

**一句话结论**：2025–2026 这轮语言演进的共同点不是语法糖，而是「运行时重写」——CPython 用自由线程和尾调用解释器拆掉 GIL 与栈帧的历史包袱，TypeScript 把编译器整体换成 Go 原生实现换来一个数量级的速度，Rust 用 2024 edition 收束十年积累的借用语义，C++26 则把反射、契约和线性代数塞进一个还没发布的 ISO 版本里。

需要先说清一件事：本标题沿用任务分配时的 2025 年基线（Python 3.13/3.14、Go 1.25、Rust 2024），但到 2026-11-15，版本线已经整体前移一档——CPython 到 3.15，Go 到 1.27，Rust 到 1.100。下文按「2026-11-15 的真实状态」写，标题保持任务编号原样，避免同名文档重复入库。

## Python：先把 GIL 和栈帧拆掉

Python 3.14（2025-10-07）是一次结构性的发布。注解改为延迟求值（PEP 649 / PEP 749），标准库内置多解释器（PEP 734），新增模板字符串 t-string（PEP 750），并给出安全的外部调试器接口（PEP 768）。执行核心换成「新型解释器」——基于尾调用的实现，替代传统的大型 switch 分发。更关键的是自由线程：官方在 3.14 发布说明里直接写「Free-threaded Python is officially supported」，也就是 PEP 779 把实验性能力转成正式支持；同时加入增量垃圾回收，标准库补上 zstandard（PEP 784），C API 有了统一的配置入口（PEP 741）。

Python 3.15（2026-10-09）继续在同一个方向上推进：

- 启动与导入：PEP 810 显式惰性导入，针对「深依赖树但大多数代码不执行」的启动慢问题；PEP 829 包启动配置文件。
- 语言与内建：PEP 814 内建 `frozendict`；PEP 661 内建 `sentinel`；PEP 798 允许推导式内解包；默认编码改为 UTF-8。
- 工程与可观测：PEP 831 默认开启帧指针，改善系统级采样剖析；PEP 799 引入独立剖析包，并附带 Tachyon 高频统计采样剖析器。
- 自由线程：PEP 803 / 820 / 793 给自由线程构建补上稳定 ABI，这是扩展生态愿意跟进的前提。
- 类型系统：PEP 728（TypedDict 额外项）、PEP 747（`TypeForm`）、PEP 800（类型系统中的不相交基类）。

发布层还有两条容易被忽略的信号。其一，官方 Windows 64 位二进制改用尾调用解释器；其二，官方 macOS 二进制默认安装自由线程支持。也就是说自由线程从「要用户自己挑一个特殊构建」变成了「官方产物的一部分」。但 JIT 依旧被称作实验性——3.15 的原话是「实验性 JIT 编译器已显著升级」，没有宣布转正，不要把它当成生产性能方案。

补丁节奏也值得注意：3.15.1（2026-10-21）与 3.15.2（2026-10-25）只隔四天，属于典型的安全/回归修复窗口。把 3.15.0 直接铺到生产之前，先看这两个补丁修了什么。

| 版本 | 发布日期 | 在本文里的意义 |
| --- | --- | --- |
| 3.13.18 | 2026-10-25 | 上一稳定线的维护尾巴，安全修复为主 |
| 3.14.0 | 2025-10-07 | 自由线程转正、注解延迟求值 |
| 3.14.10 | 2026-10-25 | 3.14 线当前补丁 |
| 3.15.0 | 2026-10-09 | 默认 UTF-8、惰性导入、稳定 ABI |
| 3.15.1 | 2026-10-21 | 首发两周后的修复 |
| 3.15.2 | 2026-10-25 | 四天内第二次修复，升级前必看 |

同一张表还能看出维护策略的细节：3.13、3.14、3.15 三条线在同一天（2026-10-25）各自发布补丁，说明安全修复是跨线同步下发的，而不是只修最新版。这对「必须留在旧版本上」的团队是个好消息，但也意味着旧线的补丁只覆盖安全与回归，不会有性能改进。

## Go：GC 换心脏，语言补上泛型方法

Go 1.26（2026-02-10）做了两件影响长期的事。语言侧，内建 `new` 允许操作数是一个表达式，用来给「可选指针字段」赋值，这对 `encoding/json` 这类用指针表示 optional 的库很实用。运行时侧，Green Tea 垃圾回收器从 1.25 的实验状态转为默认启用，官方给出的量级是：重度使用 GC 的真实程序，GC 开销下降 10–40%。pprof 也补了 `/ui/graph` 图视图，火焰图之外多了调用图视角。

Go 1.27（2026-08-19）的语言变化更受关注：方法现在可以声明自己的类型参数，也就是「泛型方法」，例如 `math/rand/v2` 里新增的 `(*Rand) N[Int intType](Int) Int`。限制仍在——接口方法不能声明类型参数，泛型方法也不能用来实现接口方法。同一版本还允许结构体字面量的键使用任意合法字段选择器、把函数类型推断推广到「泛型函数赋给匹配函数类型」的所有上下文；工具链支持 `@file` 响应文件（兼容 GCC 格式），`go` 命令则移除了 bzr 支持。

| 版本 | 发布日期 | 记忆点 |
| --- | --- | --- |
| Go 1.25.0 | 2025-08-12 | 上一基线 |
| Go 1.26.0 | 2026-02-10 | `new(表达式)`、Green Tea GC 默认 |
| Go 1.27.0 | 2026-08-19 | 泛型方法、`@file` 响应文件 |
| Go 1.27.4 | 2026-11-10 | 当前最新补丁 |

## Rust：第 100 个版本与迟到十年的 never 类型

Rust 1.100.0 于 2026-11-12 发布，正好卡在一个心理节点上。这个版本最戏剧化的条目是 never 类型 `!` 终于稳定：官方说它经历了 10 年和 5 次失败的稳定化尝试。此前 `!` 只能出现在函数返回类型里，现在可以在任意位置书写，比如 `Result<T, !>`；`Infallible` 同时变成 never 类型的别名，老 API 因此保持兼容。其余稳定项包括 Allocator API、DropGuard API、零大小类型构造、Cargo 报告未使用依赖、减少 Cargo 缓存冲突，以及 Cargo 的发布年龄下限（`min-publish-age`）能力。

2026 年的发版节奏仍是每 6 周一次：1.93.0（01-22）、1.94.0（03-05）、1.95.0（04-16）、1.96.0（05-28）、1.97.0（07-09）、1.98.0（08-20）、1.99.0（10-01）、1.100.0（11-12），其间穿插 1.93.1、1.94.1、1.96.1、1.97.1、1.98.1、1.99.1 这类漏洞修复版。语言层面的「大版本」是 2024 edition，由 1.85.0 在 2025-02-20 稳定，官方称其为「我们发布过的最大 edition」。edition 的机制是「可选的破坏性变更」：默认行为改动集中在少数点上，例如未写 `use<..>` 时 `impl Trait` 默认捕获全部参数生命周期（RPIT 生命周期捕获规则），其余大量条目是新增 lint 与迁移工具，可以用 `cargo fix --edition` 批量处理。

生态侧必须记住 2025–2026 的供应链事件：crates.io 上 evm-units 与 uniswap-utils（2025-12-03）、finch-rust 与 sha-rust（2025-12-05）被标记为恶意 crate，2026-08-20 又发生 arrayref 供应链攻击。Cargo 的发布年龄下限正是这类事件的直接回应：让新发布的版本先「晾」一段时间再被拉取。

编译器侧还有两条长期线索：2026-08-21 nightly 启用下一代 trait solver，2026-08-04 nightly 启用下一代借用检查器。两者都还没进稳定版，但会决定 2027 年之后的编译错误质量与编译时间。目标平台方面，2026-10-02 把 i686 Windows 目标降级为 std-only，说明 32 位 x86 的维护成本已经高于收益。

## TypeScript 7：把编译器换成 Go

TypeScript 7.0 于 2026-07-08 发布，官方定性是「10x faster native port」——用 Go 重写整个工具链，并且刻意保持原代码库的结构与逻辑，让两个编译器尽量给出相同结果。这个决定的意义不只是快：它把「类型检查」从 Node 单线程的 CPU 瓶颈里解放出来，让大型 monorepo 的编辑反馈接近即时。

7.1 Beta（2026-10-20）在语言侧补的是环境模块（ambient modules）中的 import attributes，让 `with { type: "json" }` 这类元数据在声明文件里也能被正确描述。对团队而言，真正的成本不在语法，而在编译器 API 与自定义插件：凡是直接调用 TypeScript 编译器内部 API 的工具，都要按 7.x 的原生实现重写一遍。

## C++26：标准还没发布，头文件已经排好队

这是本篇最需要克制的一节。截至 2026-11-15，cppreference 的 C++26 页面仍写「下一代标准」，ISO 日程引用 P1000R6（2024-05-14）；isocpp 的状态页写的是「C++26 work in progress」，下一次 WG21 会议安排在 2026-11-16 至 21 日、巴西 Búzios。也就是说 C++26 尚未作为正式 ISO 标准发布，任何「C++26 已定稿」的说法都不成立。

能确认的是它「装了什么」。新增头文件包括 `<contracts>`、`<debugging>`、`<hazard_pointer>`、`<hive>`、`<inplace_vector>`、`<linalg>`、`<meta>`、`<rcu>`、`<simd>`、`<text_encoding>`，以及 C 兼容头 `<stdbit.h>`、`<stdckdint.h>`。语言特性方面，cppreference 已列出 pack indexing（P2662R3）、无名字占位变量（P2169R4）、从 `void*` 的 constexpr 转换（P2738R1）、用户生成 `static_assert` 消息（P2741R3）、unevaluated strings（P2361R6）、基本字符集加入 `@` `$` 与反引号（P2558R2）等。

对团队的实际建议：可以按 C++26 的特性清单做技术预研和编译器矩阵测试，但不要把「等 C++26」写进排期——从标准发布到三大编译器全部落地，历史上通常还要一到两年。

## 对工程团队的实际影响

- 新项目选 Python：直接上 3.14 或 3.15。3.13 的生态优势正在消失，而 3.15 的稳定 ABI 与帧指针默认对性能剖析更友好。
- 存量 C 扩展：3.15 的稳定 ABI 只覆盖自由线程构建的一部分能力，扩展仍需针对新 ABI 重编；把 `sys._is_gil_enabled()` 加进健康检查，能一眼看出进程跑在哪种模式下。
- Go 服务：1.27 的泛型方法会让一批「包级泛型函数」收敛成类型方法，API 设计风格会变；GC 收益不需要改代码，但要重新跑一遍延迟分布。
- Rust 团队：若还在 2021 edition，迁移到 2024 的成本主要在 RPIT 生命周期捕获规则与 `unsafe` 属性的写法，`cargo fix --edition` 能覆盖大部分机械改动。
- 前端团队：TS 7 的迁移先做「工具链盘点」，把依赖编译器内部 API 的 lint、codemod、bundler 插件列出来，再谈升级。

## 常见坑与局限

- 版本号陷阱：标题写「Python 3.13/3.14」，但 3.15 已是当前稳定线；查资料时若只看标题会漏掉一整代变化。
- 自由线程不等于免费加速：它解决的是多核并行度，单线程性能与内存占用需要按官方基准单独评估。本文未逐一核对这些基准数字。
- JIT 仍在实验阶段：3.14/3.15 的官方二进制虽已包含实验性 JIT，但官方措辞始终是 experimental，不要据此调整容量规划。
- C++26 的「草案特性」与「已发布标准」必须分开写；本文明示了未发布状态。
- Rust 供应链：`min-publish-age` 只能降低窗口期风险，不能替代锁文件审计与依赖最小化。
