# MC-01 版本编号与更新节奏：从 1.20 到 26.x（2023–2026 完整时间线）

> 主题库：Minecraft 现代版本与模组（2023–2026）　｜　源文件：（纯文本条目）　｜　8,945 字符　｜　35 个片段　｜　更新于 2026-11-15
> 资料截至 2026-11-15；覆盖 2023-11 至 2026-11，重点 2024–2026。

**一句话结论**：这三年 Mojang 改的不只是内容，而是「版本」这个概念本身——更新从「一年一个大型更新」变成「一年 3–4 个季度 drop」，版本号从 `1.20.x` 这种「大版本.末位」结构退化为「只递增末位」，最终在 2026 年整体换成 `YY.D.H`（年份.第几个 drop.热修号）。对整合包作者和服主来说，真正的分水岭不是某个新生物，而是 1.20.5（物品数据组件化）、1.21.9（pack format 变双段号）和 26.1（Java 25 + 去混淆）。

## 二、节奏：从「一年一更」到「一年四个 drop」

2023 年仍是传统结构：1.20 六月上线，1.20.3 十二月收尾，中间 1.20.2 属于技术性次要更新（函数宏、实验性村民交易平衡）。全年只有两次内容发布。

2024 年 4 月的 Armored Paws 是转折点。官方随之引入 game drop 概念，并明确「每年发布 3–4 个 drop，按季度排布」。更微妙的是 1.20.3：它在 2023 年 12 月发布时只是普通次要更新，直到 2024 年 9 月官方才在社交平台上把它「追认」为 drop，并给了 Bats and Pots 这个名字。所以你现在看到的「2023 年 drop 列表」是回溯构建的，不是当时就有的。

按官方口径盘点：

- 2023 年：1.20（大版本）+ 1.20.3（追认 drop），共 2 次内容发布。
- 2024 年：Armored Paws（4 月）、Tricky Trials（6 月，大版本）、Bundles of Bravery（10 月）、The Garden Awakens（12 月），共 4 次。
- 2025 年：Spring to Life（3 月）、Chase the Skies（6 月）、The Copper Age（9 月）、Mounts of Mayhem（12 月），四个 drop 全部按季度落位。
- 2026 年：Tiny Takeover（3 月）、Chaos Cubed（6 月）、Wilderness Bound（9 月）、Fourth Drop 2026（Q4，未发布）。

节奏变化的直接后果是「热修改动内容」的频率上升：1.21.7 加了一张音乐唱片，1.21.10 修了一堆 bug，这类末位补丁已经不再是纯崩溃修复。整合包作者如果按「大版本才需要重测」的旧习惯排期，会持续踩坑。

## 三、版本号被改写了三次

### 阶段 A：1.20.x（2023-06 至 2024-04）
末位既承担热修也承担内容更新。1.20.5 是带犰狳与狼铠的内容 drop，但号段看起来像第五个补丁——这正是后来要改号的原因。

### 阶段 B：1.21.x（2024-06 至 2025-12）
结构没变，但 drop 与热修在末位上彻底混在一起：1.21.2 是收纳袋 drop，1.21.3 是它的热修；1.21.9 是铜器时代，1.21.10 是热修，1.21.11 又是 drop。靠号段已经判断不出这次更新有多大。

### 阶段 C：YY.D.H（2026 起）
官方 2025 年 12 月 2 日发布《Minecraft's new version numbering system》，正式版改为「两位年份.当年第几个 drop.该 drop 的热修号」。初始 drop 不带热修位：`26.1` 就是 2026 年第一个 drop，`26.1.2` 是它的第二次热修。带 `1.` 前缀的最后一个版本是 1.21.11。

快照命名同步改掉：沿用十二年的 `YYwNNn`（如 `25w41a`）在 2025 年 12 月 16 日终止，第一个新式快照叫 `26.1 Snapshot 1`。这对写启动器脚本、解析版本号做排序的人是硬破坏——按字符串排序会把 `26.1` 排到 `1.21.11` 前面，必须按语义版本规则处理。

| 时期 | 正式版样例 | 快照样例 | 号段语义 |
|---|---|---|---|
| 2023–2024 | 1.20.4 / 1.20.5 | 23w51a | 大版本.末位（热修与内容混用） |
| 2024–2025 | 1.21.2 / 1.21.11 | 25w41a | 末位递增，drop 与热修不可区分 |
| 2026 起 | 26.1 / 26.1.2 | 26.1 Snapshot 1 | 年份.第几个 drop.热修号 |

## 四、技术门槛的三次抬升

版本号之外，真正决定「这个包能不能跑」的是三组隐性数字。

**Java 版本**。1.18 是第一个要求 Java 17 的版本，1.20–1.20.4 一直沿用。1.20.5 起改为 Java 21，并且是第一个要求 64 位系统的正式版；1.21 作为大版本同样要求 Java 21 及以上。26.1 起抬到 Java 25（LTS）。也就是说 2023–2026 这段里，Java 门槛跨了三个大版本，任何「直接换 jar 试试」的升级路径都可能死在启动器上。

**协议号**。同协议号的客户端与服务端才互通。1.20.5 与 1.20.6 共用 766，因此互相兼容；但两者都不兼容 1.20.6-rc1——开发版的协议号把第 30 位置 1，从 `0x40000001` 起算，`1.20.6-rc1` 是 `0x400000C0`。这个设计是为了让「正式版之间跨版本兼容」与「正式版不兼容自己的快照」同时成立。26.1 是 775，26.3 是 777。

**数据版本**。存档里的 `DataVersion` 只增不减，决定开图时是否弹「此世界由更新版本保存」。26.1 的数据版本是 4786。服主回滚存档时，数据版本高于当前客户端就只能靠备份，没有降级通道。

## 六、怎么在本地确认这些数字

版本号类的元数据不必猜，游戏内与文件里都能直接读到：

- 数据版本：`/data get entity @s DataVersion`，或直接看存档目录下 `level.dat` 的 `DataVersion` 字段；25w15a 之后新增的 `/version` 命令也会把它打印到聊天栏。
- 协议号：服务端 `version.json` 里的 `protocol_version`；这也是代理（Velocity/BungeeCord）判断能否转发的依据。
- pack format：运行 `/version`，或按 F3 + V；资源的权威定义在同一份 `version.json` 的 `pack_version` 段。
- Java 要求：启动器日志第一行的 JVM 版本，或直接看崩溃报告头部的 `Java Version`。

启动器自己也会把每份元数据落盘：`.minecraft/versions/<版本 id>/<版本 id>.json` 就是这个版本的 `version.json` 副本，其中 `release_time`、`protocol_version`、`pack_version`、`javaVersion` 一应俱全。做法上与其读网页，不如直接读这个文件——它是官方产物，且与本地实际安装的版本严格对应。

对做服务器自动化的人，这一节比前面任何表格都实用：`version.json` 是官方随 jar 一起发布的结构化元数据，解析它比解析网页可靠得多。注意 1.21.9 起 `pack_version` 变成了带次段的对象，旧的「读一个整数」解析器会直接抛错。
## 七、对玩家、整合包与开发者的实际影响

**玩家**：一年四次内容更新的好处是不用等一年，坏处是「刚配好的整合包又过期了」。实践上建议锁定一个 drop 玩到底，跨 drop 升级前先备份存档。另外 26.1 之后官方不再发布混淆版 jar，这对普通玩家无感，但意味着旧的、依赖混淆映射的第三方工具（部分旧版反混淆/映射生成脚本）会直接失效。

**整合包作者**：模组生态的停留点非常集中。1.20.1 至今仍是最大的模组聚集地，原因不是它内容多，而是 1.20.5 把物品 NBT 换成了结构化数据组件，几乎所有涉及物品逻辑的模组都要重写；跨过这道坎的模组又会在 1.21.2（属性 ID 去前缀）、1.21.5（文本组件在 NBT 中改为对象）、1.21.9（pack format 双段号）连续挨打。所以「1.20.1 养老」不是懒，是成本核算的结果。

**长期存档**：三年里数据版本从 3463 抬到 4786 量级，跨 drop 打开旧图会触发「是否备份」提示。习惯上应把「每个大版本一个存档副本」制度化，而不是等升级失败再找备份；存档目录里的 `level.dat` 一旦被新版本写过，就没有官方降级路径。

**多实例并存**：由于 Java 门槛跨了三档、模组生态又分散在 1.20.1 / 1.21.1 / 1.21.5 / 26.x 几条线上，现实中同时维护 3–4 个实例已是常态。启动器里为每个实例固定 JVM 与内存，比在系统环境变量里改全局 `JAVA_HOME` 稳得多——后者会让某个实例在你切换时突然起不来。

**开发者与服主**：把 pack format 当成发布门禁。1.21.9 之后如果 `pack.mcmeta` 里还只写 `pack_format` 单值，轻则显示「不兼容」，重则直接不加载；正确写法是同时给 `min_format` 与 `max_format`。服务端侧则要注意 1.20.5 起必须 64 位 + Java 21，很多按 1.20.1 调好的 Aikar flags 与 JVM 参数需要重新核对堆大小。

## 八、常见坑

1. **把 1.21.2 当补丁**：它带收纳袋、两个新旗帜图案和稀有度重排，是完整 drop；1.21.3 才是它的热修。
2. **以为 1.20.3 一开始就叫 Bats and Pots**：发布时没有代号，2024 年 9 月才追认。查 2023 年的旧文章会发现完全找不到这个名字。
3. **1.20.2 的日期分歧**：minecraft.wiki 与官方文章均记为 2023 年 9 月 21 日，部分中文二手资料写 9 月 20 日（时区换算所致）。以 9 月 21 日为准。
4. **Java 版本混用**：1.20.5 之前用 Java 17 的实例直接跑 1.21 会报 `UnsupportedClassVersionError`；26.1 起需要 Java 25，Java 21 不够。
5. **按字符串排序版本号**：`26.1` < `1.21.11` 的字典序比较是错的，脚本里要按数字分段比较。
6. **把 1.21.11 当成 1.21.1 的重复**：两者相差十个小版本，1.21.11 是 Mounts of Mayhem，1.21.1 只是 1.21 的热修。
7. **把 26.4 当已发布**：截至 2026-11-15，26.4 只有快照（开发版首个 2026-09-22），正式版仍在 Q4 窗口内未落地。
8. **pack format 单值写法**：1.21.9+ 之后仍然只写 `pack_format` 的包会被判不兼容，这是升级后「资源包突然全红」的最常见原因。

## 九、跨 drop 升级检查清单

按这个顺序走，可以避免九成的「升完打不开」：

1. **先冻结**：把整个实例目录（含 `mods`、`config`、`saves`）复制一份，别在原目录上试。
2. **查协议号**：目标版本协议号与现有服务端不一致就必然连不上；766（1.20.5/1.20.6）与 767 之后的版本之间没有兼容层。
3. **查 Java**：1.20–1.20.4 用 Java 17，1.20.5–1.21.11 用 Java 21，26.1 起用 Java 25。启动器里给每个实例单独指定 JVM，而不是改全局。
4. **查 pack format**：1.21.9 之后确认 `pack.mcmeta` 已改为 `min_format`/`max_format`；1.21.9 对应 88.0，1.21.11 对应 94.1，26.1 对应 101.1。
5. **查模组线**：跨过 1.20.5 的包基本等于重做，跨过 1.21.2 要检查属性 ID，跨过 1.21.5 要检查文本组件在 NBT 里的形态。
6. **最后才动存档**：先在新建世界验证能进、能跑 20 分钟不崩，再迁移存档；数据版本只增不减，回滚只能靠第 1 步的备份。
