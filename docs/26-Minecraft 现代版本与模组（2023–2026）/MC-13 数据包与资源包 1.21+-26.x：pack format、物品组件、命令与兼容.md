# MC-13 数据包与资源包 1.21+/26.x：pack format、物品组件、命令与兼容

> 主题库：Minecraft 现代版本与模组（2023–2026）　｜　源文件：（纯文本条目）　｜　9,666 字符　｜　40 个片段　｜　更新于 2026-11-15
> 资料截至 2026-11-15；覆盖 2023-11 至 2026-11，重点 2024–2026。

**一句话结论**：2024–2026 的数据包/资源包体系经历了两次结构性变化——1.20.5 把物品 NBT 换成数据组件、1.21.9 把 `pack_format` 换成 `min_format`/`max_format` 并引入「主.次」版本号；1.21 起目录名统一改成单数，1.21.4 又给资源包加了独立的「物品模型定义」层。写包的人如果只会 1.20.1 那套，几乎每个环节都会踩坑。

## pack.mcmeta：从 `pack_format` 到 `min_format`/`max_format`

1.20.2（23w31a）给 `pack.mcmeta` 加了 `supported_formats` 与 `overlays`，让一个包可以声明「我支持 42 到 45」并按区间套用子包。1.21.9（25w31a）把这套推倒重来：

- `pack_format` 变为**可选**，只有在包还支持旧格式（数据包 < 82、资源包 < 65）时才必须保留；
- 新增**必需**的 `min_format` 与 `max_format`，值可以是整数，也可以是 `[主, 次]` 数组；
- `supported_formats` 被移除（同上，仅向下兼容时必须保留）；
- `overlays[].formats` 被移除，改成每个 overlay 自己的 `min_format` / `max_format`。

单写一个整数等于「主版本 + 次版本 0」，例如 `"min_format": 84` 等价于 `[84, 0]`；`max_format` 写整数则表示「该主版本下任意次版本」。所以 26.1 的包最稳的写法是：

```json
{
  "pack": {
    "description": "Example 26.1 pack",
    "min_format": [84, 0],
    "max_format": [84, 0]
  }
}
```

如果这个包还要能在 1.21.8 上跑，就必须同时保留旧的 `pack_format: 64` 与 `supported_formats`，否则旧版本会直接判定不可用。这也是「一个包同时支持多个大版本」在 1.21.9 之后变麻烦的根本原因。

次版本（`88.0` 里的 `.0`）是给**非破坏性改动**准备的：官方明确说 minor 在「不做破坏性改动」时递增，所以 88.0 与 88.1 之间通常可以互装，但 88.x 与 89.0 不行。

### `filter` 与 `overlays` 的两个细节

`filter.block` 是「过滤掉低优先级包里的文件」的机制：`namespace` 与 `path` 都是正则，省略即匹配全部。它常被用来做「我这个包接管了这一批纹理，不要再用下面那个包的」，比逐个覆盖文件省事。`overlays.entries` 的顺序有意义，列表里第一个先生效；每个 overlay 目录里同样可以有 `assets/` 与 `data/`，但目录名只能是 `a-z`、`0-9`、`_`、`-`、`.`。

```json
{
  "pack": { "description": "multi-version pack", "min_format": [65, 0], "max_format": [84, 0] },
  "overlays": {
    "entries": [
      { "directory": "v26_1", "min_format": [84, 0], "max_format": [84, 0] }
    ]
  }
}
```

注意 overlay 目录里不能再放 `pack.mcmeta` 与 `pack.png`，它们会被忽略；这是很多人把 overlay 写成「包里再套一个包」后失效的原因。

## 目录结构：单数、注册表化、以及新增的文件夹

1.21 起 `data/<namespace>/` 下的目录统一改为单数：`loot_tables` → `loot_table`、`functions` → `function`、`tags/items` → `tags/item`。旧名不会报错，但会被忽略，表现是「文件明明在，游戏就是不认」。

| 位置 | 内容 | 备注 |
|---|---|---|
| `data/<ns>/function/*.mcfunction` | 函数 | 1.21 起单数 |
| `data/<ns>/tags/<registry>/*.json` | 各类标签 | 标签默认合并，`"replace": true` 才覆盖 |
| `data/<ns>/enchantment/`、`damage_type/`、`jukebox_song/`、`instrument/` | 数据驱动注册表 | 属于「实验性设置」，`/reload` 不生效 |
| `data/<ns>/dialog/`、`timeline/`、`world_clock/` | 1.21.6 / 1.21.11 / 26.1 新增 | 版本不对会整体加载失败 |
| `assets/<ns>/items/*.json` | 物品模型定义 | 1.21.4 起必需 |
| `assets/<ns>/models/`、`blockstates/`、`textures/`、`lang/`、`sounds/` | 传统资源 | 路径规则未变 |
| `assets/<ns>/equipment/`、`atlases/`、`font/`、`post_effect/` | 装备外观、图集、字体、后处理 | 1.21.2 起装备独立成文件 |

「实验性设置」这条要单独记：动态注册表（附魔、画作、伤害类型、维度等）在数据包里定义时，游戏会把整个世界标记为使用实验性内容，单人会弹警告，Realms 直接拒绝上传。静态注册表（标签、配方、战利品表、函数）才能靠 `/reload` 热更。

## 物品组件：数据包作者的主战场

1.20.5 之后，物品的附加数据从 NBT 变成命名空间化的组件，写法从「往 `tag` 里塞」变成「在 `components` 里写键」：

```json
{
  "type": "minecraft:stone",
  "components": {
    "minecraft:custom_name": "{\"text\":\"测试\"}",
    "minecraft:item_model": "mymod:custom_stone",
    "minecraft:max_stack_size": 16
  }
}
```

组件数量已经过百（`custom_data`、`food`、`equippable`、`enchantments`、`attribute_modifiers`、`blocks_attacks`、`attack_range`、`dye` 等），而且每个大版本都在增删：1.21.5 删掉了 `hide_tooltip` 与 `hide_additional_tooltip`，统一用 `tooltip_display`；1.21.11 加了 `attack_range`；26.1 加了 `minecraft:dye`。写通用模板时把组件名硬编码进 KubeJS 脚本或数据包，是跨版本失效的头号原因。

### 客户端物品模型：1.21.4 新增的一层

1.21.4 起，物品的渲染不再由 `models/item/<id>.json` 直接决定，而是由 `assets/<ns>/items/<id>.json`（物品模型定义）指向模型。触发方式是 `minecraft:item_model` 组件，默认取物品 id。这一层的价值是可以在**同一个模型文件**上按组件、交互状态、库存位置切换不同模型（composite、condition、select 等），代价是「只写模型不写定义」会显示紫黑方块。

常见字段包括 `model`（基础模型）、`hand_animation_on_swap`（切换物品时是否播动画）、`oversized_in_gui`（1.21.6 加入，允许超出 GUI 槽位）。做自定义武器、饰品、GUI 图标时，这一层几乎绕不开。

## 命令侧的变化

| 命令 | 版本 | 用途 |
|---|---|---|
| `/datapack create <id>` | 1.21.6 | 直接在当前世界生成一个空数据包目录 |
| `/version` | 1.21.6 | 打印游戏版本、协议号与数据版本 |
| `/dialog show` | 1.21.6 | 打开数据包定义的对话框 |
| `/rotate` | 1.21.2 | 旋转实体，做展示模型很方便 |
| `/stopwatch` | 1.21.11 | 计时器，可被 `execute if stopwatch` 读取 |
| `/time of <clock>` | 26.1 | 配合 world clock 的多时钟时间系统 |

另外 21.6 起 `datapack` 命令多了 `create` 子命令，这对做包的人是实打实的提速：不用再手动建目录、写 `pack.mcmeta` 再拖进 `datapacks/`。

## 一个最小可用的数据包

把上面的规则拼起来，26.1 上一个「进世界就给玩家发一本自定义书」的包，目录是这样：

```
mypack/
├── pack.mcmeta
└── data/
    └── mypack/
        ├── function/
        │   └── give_book.mcfunction
        └── tags/
            └── function/
                └── load.json
```

`pack.mcmeta` 写 `min_format` 与 `max_format` 都为 `[84, 0]`；`load.json` 里 `{"values": ["mypack:give_book"]}`；函数里用 `give @s minecraft:written_book[minecraft:custom_name='{"text":"指南"}']` 这类组件语法。三条规则记住就不会错：**`pack.mcmeta` 是唯一必需文件**、**标签默认合并**、**函数要挂到 `minecraft:load` 才会自动执行**。

验证方式也不难：进世界后 `/datapack list` 看有没有你的包，`/reload` 看有没有报错，`/function mypack:give_book` 手动跑一次。如果 `/datapack list` 里没有，先查目录层级（`data/<ns>/` 多一层或少一层是最常见问题）。

## 资源包：纹理、字体、音效的现状

资源包这边 2024–2026 的变化没有数据包剧烈，但有几处必须知道：

- **`assets/<ns>/lang/zh_cn.json` 仍是纯键值对**，但 1.21.5 起 NBT 里的文本组件存成对象而非 JSON 字符串，命令里写 `{"text":"..."}` 与 SNBT 的 `{text:"..."}` 要区分场景。
- **字体**用 `assets/<ns>/font/*.json`，provider 支持 `bitmap`、`ttf`、`space`、`unihex`、`reference`；做中文自定义字体时 `unihex` 仍是最稳的方案。
- **图集**用 `assets/<ns>/atlases/*.json` 声明哪些纹理进哪个图集，1.19.3 之后不再靠目录扫描。
- **装备外观**在 1.21.2 之后独立为 `assets/<ns>/equipment/*.json`，盔甲与鞘翅的模型/纹理分层由它控制，不再塞在物品模型里。
- **音效**仍是 `assets/<ns>/sounds.json` + `assets/<ns>/sounds/*.ogg`，但 1.21.9 起环境属性（environment attributes）会影响雾、天空、音效等客户端表现，做维度/生物群系资源包时要一起改。

物品模型那一层（`items/*.json`）是资源包里唯一「新增一层结构」的地方：它把「用哪个模型」和「模型长什么样」拆开，好处是同一模型可被多个物品复用，坏处是概念多了一层，初学者经常只改 `models/item` 而忘了 `items`。

## 从 1.20.1 包迁移的检查清单

| 检查项 | 1.20.1 写法 | 1.21+/26.x 写法 |
|---|---|---|
| 目录名 | `loot_tables/`、`functions/`、`tags/items/` | `loot_table/`、`function/`、`tags/item/` |
| 元数据 | 仅 `pack_format: 15` | `min_format` / `max_format`（旧字段按兼容需要保留） |
| 物品数据 | `tag: {CustomModelData: 1}` | `components: {"minecraft:custom_model_data": ...}` |
| 提示隐藏 | `HideFlags` | `minecraft:tooltip_display` |
| 附魔 | `Enchantments` 列表 | `minecraft:enchantments` 组件（命名空间 id） |
| 物品渲染 | `models/item/<id>.json` 直接生效 | 还需 `items/<id>.json` 并由 `item_model` 指向 |

迁移时最省力的顺序是：先改目录名与 `pack.mcmeta`（让包能加载），再逐个把物品 NBT 换成组件（让内容正确），最后补 `items/*.json` 与装备文件（让外观正确）。反过来做，会在前两步反复被「包加载失败」打断。

## 对整合包作者与服主

数据包在整合包里通常有三种放法，选错会让人以为是包坏了：

- **世界级**：`saves/<world>/datapacks/`，只对这个存档生效，服务器则是 `world/datapacks/`；
- **资源包级**：`resourcepacks/`，只影响客户端外观，服务器无法强推；
- **打包进模组**：模组 jar 内的 `data/` 与 `assets/` 会被当作内置包加载，优先级最低，适合放「默认值」而不是覆盖。

包的加载顺序记录在 `level.dat` 里，`/datapack list` 可以看到 enabled/disabled 两组，用 `/datapack enable "file/xxx"` 调整。整合包作者如果要在更新时替换某个包，注意同名包不会自动替换旧包，而是按顺序叠加——后加载的覆盖先加载的同名文件，标签则默认合并。

另一个实用点：1.21.6 的 `/datapack create` 生成的是**当前世界**的空目录包，位置正好在 `world/datapacks/` 下，做快速验证比手工建目录快很多。

## 兼容策略：一个包怎么撑过多个版本

1. **优先用 `overlays`**：把 1.21.8 与 26.1 的差异文件放进 `overlays/` 子目录，各自声明 `min_format`/`max_format`，主目录放共同部分。
2. **同时保留新旧字段**：要兼容 1.21.8 及更早，`pack_format` + `supported_formats` 必须留着；只支持 1.21.9+ 才删除。
3. **版本相关的内容做「降级占位」**：新组件（如 `attack_range`）在旧版本会被忽略并报一条警告，但整个物品仍能加载，比直接报错好。
4. **实验性内容单独成包**：把附魔、维度这些动态注册表放进独立的「实验包」，主包只放标签/配方/战利品表，这样主包仍可 `/reload`。

## 常见坑

1. 目录名还是复数（`loot_tables`、`functions`），1.21+ 直接忽略，且没有任何报错。
2. 1.21.9+ 还只写 `pack_format`，包能加载但显示「为旧版本制作」，`min_format` 缺失时部分版本会拒绝。
3. 资源包只写了 `models/item/*.json` 就以为完事，1.21.4+ 缺 `items/*.json` 会显示紫黑方块。
4. 把附魔/维度定义放进主数据包，结果整个世界被标记为实验性，Realms 传不上去。
5. 用 1.20.4 的 `custom_model_data`（整数）写法，1.21.4 之后它已变成组件，旧写法被忽略。
6. 26.2 起实体谓词遇到未知字段直接报错，过去「多写几个字段碰运气」的包会整包加载失败。
