# AG-03 RAG 2.0 与检索工程：混合检索、重排、GraphRAG、Contextual Retrieval、评测

> 资料截至 2026-11-15；覆盖 2023-11 至 2026-11，重点 2024–2026。

## 一、结论先行

“RAG 2.0”不是一个新算法，而是把 RAG 从“向量库 + 拼 prompt”改造成三段可分别度量的工程：**索引**（切块、上下文化、图谱化）、**检索**（混合召回 + 重排）、**上下文**（放什么、放多少、何时放）。2024 年 Anthropic 的 Contextual Retrieval 给出了这套改造最早的一组硬数字，2025 年的“上下文工程”则把最后一段也纳入了设计范围。

五个判断：

1. **纯向量召回已经不够**。BM25 仍是强基线，混合检索是默认配置；重排负责把“召回得全”换成“排得准”。
2. **切块的真正问题不是大小，而是上下文丢失**。Contextual Retrieval 用“给每个块补一段所属文档的说明”把失败检索降低 49%，加重新排序后降低 67%。
3. **GraphRAG 解决的是“全局性问题”**，不是替代向量检索。它的索引成本高，查询模式要按问题类型选（Global / Local / DRIFT）。
4. **评测要分两层**：检索层看 Recall@k、nDCG@10，生成层看忠实度与相关性；只用端到端打分，无法定位问题出在召回还是生成。
5. **“即时检索”正在成为第三极**：不改索引，让 agent 用文件路径、SQL、grep 在运行时取数。它适合代码与结构化数据，不适合需要语义模糊匹配的大语料。

## 二、两种范式：预索引 vs 即时检索

| 范式 | 索引成本 | 首字延迟 | 擅长 | 典型失败 |
| - | - | - | - | - |
| 朴素 RAG（单路向量） | 低 | 低 | 单跳事实问答 | 专有名词、缩写、精确匹配失效 |
| 混合检索 + 重排 | 中 | 中 | 大多数企业知识库 | 多跳、聚合、跨文档比较 |
| GraphRAG | 高（LLM 抽实体+社区摘要） | 中高 | 全局概括、跨文档关系 | 索引贵、增量更新难 |
| 即时检索（agentic search） | 近零 | 高（多轮工具） | 代码库、数据库、长文档定位 | 语义召回弱、依赖工具质量 |

Anthropic 在 2025-09-29 的上下文工程文章里把第三极讲得最清楚：不预处理全部数据，而是让 agent 持有“轻量标识符”（文件路径、保存的查询、链接），运行时用工具把数据取进上下文。Claude Code 就是靠写定向查询、用 `head`/`tail` 看片段，避免把整张表读进窗口。代价是每轮都要花 token 与时间做探索，所以它和预索引不是取代关系，而是按语料形态分工。

## 三、索引：把上下文写回块里

传统切块把文档切成几百 token 的小块，独立编码。问题很直接：一块写着“该公司营收增长 12%”，离开文档后没人知道“该公司”是谁。

Anthropic 的 Contextual Retrieval 用两步修这个洞：**Contextual Embeddings**（先让模型为每块生成一段“它在整篇文档中的位置与主题”的说明，再把说明拼在块前一起嵌入）与 **Contextual BM25**（同一份增强文本也进 BM25 索引）。官方给出的结果是失败检索减少 49%，叠加重新排序后减少 67%。

三个可复用的工程结论：

- **上下文不一定要塞进向量**。同一份增强文本同时喂稠密与稀疏索引，收益是乘出来的。
- **小语料别上 RAG**。官方明确说知识库小于 200,000 token（约 500 页）时，直接全量放进 prompt 更简单，配合 prompt caching 可把延迟降到原来的二分之一以下、成本最多降 90%。
- **切块策略要匹配问题类型**。事实型问题适合小块高精度；概括型问题需要父子块或摘要树。

另一条路线是 **late chunking**（arXiv 2409.04701，2024-09）：先用长上下文嵌入模型编码整篇文档的所有 token，再在 transformer 之后、均值池化之前切块。这样每个块的向量都“见过”全文，不需要为每块单独生成说明，但要求嵌入模型支持长输入。**RAPTOR**（arXiv 2401.18059）则递归聚类并摘要，形成树状索引，用不同抽象层级回答不同粒度的问题。

## 四、召回：混合检索是默认解

单路向量的软肋是精确匹配：产品型号、错误码、人名、缩写。BM25 恰好擅长这些，代价是对同义改写不敏感。两者互补，所以生产系统普遍并行召回再融合。

融合最常用的是 **Reciprocal Rank Fusion（RRF）**：对每个候选按 `1/(k+rank)` 累加，`k` 常取 60。它只用排名不用分数，避免了不同检索器分数量纲不一致的问题——这是它比“加权求和”更稳的原因。调参空间主要在候选深度（每路取多少）与最终截断，而不是权重。

嵌入模型的选择也在收敛。**BGE-M3**（arXiv 2402.03216）一个模型同时输出稠密、稀疏（类 SPLADE）与多向量三种表示，支持 100 多种语言、最长 8,192 token。这意味着“混合检索”可以不再维护两套模型与两套索引，代价是存储与打分复杂度上升。

| 召回/重排手段 | 机制 | 成本 | 擅长 | 主要弱点 |
| - | - | - | - | - |
| BM25 | 词频与逆文档频率 | 极低 | 精确词、代码、编号 | 同义改写 |
| 稠密向量 | 双塔嵌入 + ANN | 低 | 语义相似、跨语言 | 专名、长尾实体 |
| 稀疏学习（SPLADE / BGE-M3 sparse） | 学习型词权重 | 中 | 兼顾精确与泛化 | 索引膨胀 |
| Late interaction（ColBERT 系） |  token 级最大相似 | 高（存储） | 细粒度匹配 | 向量库支持有限 |
| Cross-encoder 重排 | 查询-文档联合编码 | 中高（每对一次前向） | 精排前 20–100 | 不能全库扫 |
| LLM 重排 | 让模型判断相关性 | 最高 | 复杂语义、可解释 | 延迟与成本 |

查询侧还有三类被论文验证过的增强，值得按需引入。**HyDE**（arXiv 2212.10496）先让模型写一段假想答案再拿它去检索，缓解“问题与文档措辞不对齐”；**Self-RAG**（arXiv 2310.11511）让模型自己决定要不要检索、并对生成结果自我批判；**CRAG**（arXiv 2401.15884）在检索后加一个轻量评估器，判定召回质量差时触发纠错（改写查询或退化为联网/全文检索）。三者的共同点是**把检索从一次性动作变成带反馈的循环**，代价是延迟与调用次数上升。工程上建议先只上 HyDE 这类低成本改写，确认召回瓶颈后再引入评估器。

## 五、重排：把“召回全”换成“排得准”

重排的定位是**只处理少量候选**。典型链路是：混合召回取前 50–100，cross-encoder 重排到前 5–10，再进生成。Anthropic 的 67% 数字就是“Contextual Retrieval + reranking”的组合效果，说明两者不是替代而是叠加。

三种重排的取舍：

- **Cross-encoder**：查询与文档拼一起过模型，精度最高的一档，但每对都要一次前向，只能做小候选集。
- **Late interaction**：预存 token 向量，查询时做最大相似，精度接近 cross-encoder、可离线索引，代价是存储放大数倍。
- **LLM 重排**：把候选列表交给模型排序或逐条打相关性，适合需要解释的场景，但延迟与成本最高，且要防“位置偏好”。

一个常被忽略的细节：**重排会放大召回偏差**。如果正确文档根本没进候选集，重排再强也救不回来。所以先看 Recall@50，再看 nDCG@10，顺序不能反。

## 六、GraphRAG：为全局性问题建索引

微软的 GraphRAG（arXiv 2404.16130，2024-04）流程是：从原文抽取实体与关系构成知识图谱，做社区检测形成层级，再为每个社区生成摘要；查询时按问题类型选择路径。官方 Python 库 `graphrag` 当前版本 3.3.0，查询模式包括 **Global Search**（用社区摘要回答“整体在讲什么”）、**Local Search**（围绕实体及其邻居回答具体问题）与 **DRIFT Search**（混合全局与局部，先粗后细）。

它解决的问题很具体：传统 RAG 在“这批文档的主要风险是什么”“几家供应商的策略差异”这类**需要跨文档聚合**的问题上表现差，因为召回的总是几个局部片段。GraphRAG 用预生成的社区摘要把“全局视图”也变成可检索的对象。

代价同样具体：索引阶段要跑大量 LLM 调用（抽实体、写摘要），成本随语料线性上升；增量更新麻烦，实体消歧与关系抽取的错误会固化进图；对“单点事实查询”它并不比向量检索更好。因此合理的做法是**按问题类型路由**：事实型走向量/混合，聚合型走 GraphRAG，别指望一个索引通吃。

## 七、评测：分两层，别只看一个分

检索层与生成层要分开测，否则无法归因。

| 指标 | 层级 | 测什么 | 数据要求 | 常见误用 |
| - | - | - | - | - |
| Recall@k | 检索 | 正确文档是否进候选 | 查询-文档标注 | k 取得太小，误判召回差 |
| nDCG@10 | 检索 | 排序质量 | 相关性分级 | 用二值标注算分级指标 |
| Context Precision | 检索/上下文 | 命中块是否排在前面 | 查询+检索结果 | 与 Recall 混用 |
| Context Recall | 检索/上下文 | 参考答案的信息是否被覆盖 | 需参考答案 | 参考答案本身不全 |
| Faithfulness | 生成 | 回答是否只依据上下文 | 回答+上下文 | 模型自评放水 |
| Response Relevancy | 生成 | 回答是否切题 | 问题+回答 | 长回答虚高 |
| Noise Sensitivity | 上下文 | 无关块是否带偏答案 | 需注入噪声 | 噪声构造不真实 |

RAGAS（当前 0.4.4）把上述指标做成了可调用实现，并提供测试集生成（单跳、多跳、以人为中心）与多语言适配。它的价值是提供统一口径，风险是把 LLM 当裁判：同一批数据换模型，分数会漂移。工程上应固定裁判模型与 prompt 版本，并把人工抽检作为校准锚点。

检索层的经典基准是 **BEIR**（arXiv 2104.08663）：18 个数据集、覆盖词法/稀疏/稠密/late-interaction/重排五类系统，专门测零样本跨域泛化。它提醒一件事——在分布外数据上，复杂模型未必赢过 BM25，所以“换更强的嵌入模型”不能替代“在你的语料上做消融”。

## 八、参数起点与实验方法

以下是工程经验起点，不是官方推荐值，必须用自己的标注集验证：

| 参数 | 起点 | 调整方向 |
| - | - | - |
| 块大小 | 256–512 token | 事实型偏小，概括型偏大或用父子块 |
| 块重叠 | 10%–20% | 表格/条款类可更高 |
| 混合召回候选 | 每路 50–100 | 先保 Recall@50，再谈精排 |
| 重排深度 | top 20–50 进，出 5–10 | 延迟敏感就减深度，不要减召回 |
| RRF 常数 k | 60 | 候选质量差时适当增大 |
| 生成上下文 | 3–8 块 | 超过 8 块通常只增加噪声 |

实验设计上，三件事决定结论是否可信：**固定语料快照**（否则指标不可复现）、**分层标注集**（单跳/多跳/聚合/拒答各若干）、**单变量消融**（一次只改切块或只改重排）。最常见的错误是同时换嵌入模型、切块大小和 prompt，然后宣称“新方案提升 20%”——这种数字无法归因，也无法迁移。

## 九、落地顺序

1. 先建 100–300 条分层评测集，再动架构；没有评测集的优化都是猜。
2. 上混合检索 + RRF，测 Recall@50；这一层通常收益最大、成本最低。
3. 加 cross-encoder 重排，测 nDCG@10 与端到端忠实度。
4. 若聚合型问题占比高，再评估 GraphRAG；先用小语料算清索引成本。
5. 若语料是代码或高度结构化数据，优先做即时检索工具，而不是硬套向量库。

## 不确定项

- 49% / 67% 是 Anthropic 在其自建语料与流程上的结果，不能直接外推到中文企业语料；本文只把它当作方向性证据。
- GraphRAG 的索引成本没有官方统一口径（随模型价格、语料规模、实体密度变化），本文不给具体金额或耗时。
- RRF 的 `k=60` 来自检索工程惯例与原始论文设定，不同实现默认值可能不同，需查所用组件文档。
- RAGAS 0.4.4 的指标实现细节（提示词、判定阈值）未逐行核对，分数跨版本不可直接比较。
- 表中“参数起点”是经验值而非官方建议，缺少对照实验时不应写进验收标准。
- 中文/多语场景的嵌入与重排选型，本次未查到可复现的公开横评，故不推荐具体模型。
