# AG-06 上下文工程与记忆：context rot、压缩、长期记忆、AGENTS.md 约定

## 一句话结论

2025 年之后，「上下文工程」从提示词技巧变成了独立的工程学科，原因有三件事同时发生：Chroma 的 context rot 报告证明长上下文并不可靠、压缩（compaction）从「你自己写摘要」变成平台能力、AGENTS.md 把「项目约定放哪」变成了跨厂商的纯文本事实标准；三者合起来指向同一个判断——上下文不是仓库，是工作台，价值不在能堆多少，而在每一轮留给模型的都是当下最该看的东西。

## 一、context rot：长上下文为什么不可靠

2025 年 7 月 14 日，Chroma 发布技术报告《Context Rot: How Increasing Input Tokens Impacts LLM Performance》，作者是 Kelly Hong、Anton Troynikov 和 Jeff Huber。报告评测了 18 个模型，包括当时的 GPT-4.1、Claude 4、Gemini 2.5 与 Qwen3，结论一句话可以概括：模型并不均匀地使用上下文，输入越长，表现越不可靠，而且退化方式并不规则。

这项研究的方法比结论更值得学。它没有直接用经典的 Needle in a Haystack（NIAH），而是把 NIAH 拆开做变量控制：让 needle 与问题之间是语义匹配而非字面匹配、加入干扰项、改变 haystack 的结构；再加两项任务——LongMemEval 的对话式问答，以及一个「重复单词」的合成任务。选择这些任务的逻辑是：**如果连最简单、最受控的任务都会随长度退化，那退化就不是任务难度造成的，而是上下文机制本身的性质**。

这件事对工程的直接冲击是：过去判断「能不能放进去」看窗口大小，现在要看「放进去还能不能用」。一个 200K 窗口的模型，把 150K 的工具输出塞进去，形式上没超限，实际上关键信息已经被稀释。

| 失效形态 | 表现 | 对应手段 |
| --- | --- | --- |
| 长度退化 | 同样的问题，长上下文下答对率下降 | 压缩、分段处理、只取相关片段 |
| 位置敏感 | 关键信息在中间被忽略（lost in the middle 类现象） | 把关键约束放头尾、结构化重排 |
| 干扰项淹没 | 大量相似内容让模型抓错对象 | 去重、标注来源、显式编号 |
| 结构混乱 | 层级与归属不清，模型误读作用域 | 用明确分隔与标题，工具结果单独包裹 |

## 二、上下文工程到底在管什么

Anthropic 在 2025 年 9 月 29 日的工程博客里给了一个可操作的定义：上下文工程是「在推理期间策划与维护最优 token 集合」的策略集合，它管的不只是提示词，还包括系统指令、工具定义、Model Context Protocol 暴露的能力、外部数据、以及消息历史。文章把它定位成 prompt engineering 的自然演进——早期做 LLM 应用，主要工作是写对系统提示；现在做 agent，主要工作是管理一个会不断膨胀的状态。

这个定义里最容易被忽略的是「工具定义也占上下文」。一个暴露 40 个工具的 agent，光 schema 就可能吃掉几千 token，而且这些 token 每一轮都在。于是有了 2025 年 11 月 4 日那篇《Code execution with MCP》的思路：与其把工具结果一条条塞回上下文，不如让模型写代码、在沙箱里处理数据，只把结论带回来。这不是省 token 的小技巧，而是把「上下文」和「计算」解耦。

## 三、压缩：三种做法，和它们各自的代价

| 压缩方式 | 做什么 | 省多少 | 代价 |
| --- | --- | --- | --- |
| 摘要压缩（compaction） | 把历史对话改写成摘要，替换原文 | 通常最大 | 细节与数字最易丢，摘要本身会二次失真 |
| 工具结果清除（context editing） | 删掉旧的工具返回，保留调用记录 | 中等 | 需要重新取数时得再调一次工具 |
| 图像裁剪与淘汰 | 缩图、只留最近若干张截图 | 对 computer-use 最有效 | 早期画面证据消失，难以回溯 |

2025 年 9 月 29 日，Anthropic 同时发布了工程博客和产品能力：context editing 与 memory tool，配合 Claude Sonnet 4.5，目标很明确——让长时任务不必在「截断 transcript」和「性能退化」之间二选一。到 2026 年，官方 computer-use 参考实现的生产化清单里已经直接写了 server-side compaction，说明这件事从「应用自己想办法」变成了「平台提供能力」。

工程上真正难的不是调用压缩，而是**决定什么时候压、压掉什么**。三条经验：

1. **按信号触发，不按轮数触发**。轮数是粗指标；更可靠的是「上下文占用超过阈值」或「同一类工具结果重复出现 N 次」。
2. **先压过程，后压结论**。工具返回的原始 JSON 可以压成一句结论，但用户给的约束、已经确认的事实、失败的尝试不能压。
3. **压缩要留锚点**。摘要里保留原始消息的 id 或步骤号，出问题能回查；否则压缩就是不可逆的信息销毁。

## 四、长期记忆：文件、工具、服务三种形态

| 形态 | 代表 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 文件即记忆 | `AGENTS.md`、`CLAUDE.md` 等项目约定文件 | 人可读可改、可进版本库、跨工具 | 需要人工维护，容易过期 |
| 平台记忆工具 | Anthropic memory tool（2025-09-29） | 跨会话持久、由模型自主读写 | 写入质量依赖模型判断，可能记错 |
| 外部记忆服务 | Mem0、Zep、LangMem 一类 | 可检索、可规模化管理 | 多一层依赖与延迟，评测口径不一 |

三类形态的分工在实践中逐渐清晰：**项目级不变的约定放文件，会话级的偏好放平台记忆，海量可检索的知识放外部服务**。把三者混用是常见错误——把「这个仓库用 pnpm」写进向量库，每次都要检索一次，既慢又可能检索不到；把「用户这次想要简短回答」写进 AGENTS.md，会污染所有后续会话。

记忆的另一个隐性成本是**写入即偏见**。模型自己决定记什么，就会倾向于记「它以为自己理解了」的东西；一旦记错，后续每一轮都在错误前提上推理。所以可靠的系统通常要求：记忆写入要可审计（记了什么、依据哪条消息）、要可删除、并且定期让人过一遍。

## 五、AGENTS.md：为什么这个约定赢了

`AGENTS.md` 的定位非常朴素：README 是给人看的，`AGENTS.md` 是给 agent 看的。它把「构建命令、测试命令、代码风格、环境陷阱」这些容易把 README 撑爆的内容单独放一处，位置固定、格式纯文本、不绑定厂商。官方页面给出的采用规模是 60k+ 开源项目，支持方包括 Codex、Jules、Factory、Aider、goose、opencode、Zed、Warp、VS Code、Devin、UiPath、Junie、Amp、Cursor、RooCode、Gemini CLI、Kilo Code、Semgrep、GitHub Copilot coding agent、Ona、Windsurf、Augment Code 等二十余种工具。

它赢的原因不是技术先进，而是**可预测**：agent 不需要猜「这个项目的约定在哪」，人也不需要为每个工具维护一份。

| 该写 | 不该写 |
| --- | --- |
| 安装、启动、测试的确切命令 | 与 README 重复的项目介绍 |
| 代码风格与禁用写法（如必须 strict、不许 any） | 会很快过期的临时状态（当前分支、临时开关） |
| 目录结构与「改哪里找什么」 | 长篇架构文档（应放独立文档并链接） |
| 已知陷阱（如某测试需要本地服务） | 密钥、内网地址、个人隐私 |
| 提交与评审约定 | 模型无法执行的愿望（「请写高质量代码」） |

写法上有两条被反复验证的经验：一是**命令必须可直接复制执行**，写「用 pnpm 安装」不如写 ``pnpm install --filter web``；二是**约束要写成否定句**，明确「不要用默认导出」「不要新增依赖」，比正面描述更能约束模型行为。

## 六、一个可落地的上下文预算模板

把「省着用」变成可执行的规则，最简单的办法是给每类内容分配预算。下表是一个经验起点，不是标准答案，实际要按任务类型调：

| 内容类别 | 建议占比 | 超限时先动谁 |
| --- | --- | --- |
| 系统指令与策略 | 10%–15% | 不动；必要时拆成按场景加载的子指令 |
| 工具 schema | 10%–20% | 先合并工具，再按需加载（不要一次全挂） |
| 检索/文件内容 | 25%–35% | 先重排与截断，再换更小的片段 |
| 对话与工具历史 | 25%–35% | 先清工具原始返回，再摘要压缩 |
| 预留输出空间 | 10%–15% | 不动；它决定模型能不能把话说完 |

这套分配的意义在于把争论变成算术：当有人说「再加一个工具吧」，你要看的是工具 schema 那 10%–20% 还剩多少；当上下文快满，你知道先砍历史而不是先砍指令。

阈值也要具体。一个常见的做法是设两条线：占用到 60% 触发「轻压缩」（清旧工具结果、淘汰旧截图），到 80% 触发「重压缩」（摘要历史 + 只保留最近若干轮原文），并在这两条线各记一个日志事件，方便事后判断是压缩太早还是太晚。压缩本身也要留余量——摘要同样占 token，压完不是零成本。

## 七、对团队的实际影响

- **上下文预算要像内存一样管**。给系统提示、工具 schema、检索结果、历史消息各设上限，超了就压，而不是等窗口满。
- **压缩策略要写进设计文档**。什么能压、什么不能压、压完怎么回查，这三件事在事故复盘时会被反复追问。
- **把 AGENTS.md 当代码维护**。进版本库、随架构变、在 CI 里检查命令是否还能跑；一份腐烂的 `AGENTS.md` 比没有更糟。
- **记忆要有出口**。任何自动写入的记忆都必须能被列出、被删除、被人工纠正，否则它会变成组织里没人敢动的黑箱。

## 八、常见坑

1. **把摘要当原文用**。摘要丢掉的往往正是数字、否定条件、例外，二次引用会放大误差。
2. **压缩掉约束**。用户说「不要动数据库」，压完只剩「用户要求优化性能」，事故就是这么来的。
3. **工具 schema 膨胀**。每加一个工具都在每轮付费，且稀释注意力；能合并的合并，能按需加载的按需加载。
4. **用向量库存一切**。「永远要跑测试」这种恒定约束不该走检索。
5. **记忆污染**。模型把自己的猜测写进长期记忆，下次当成事实用。
6. **AGENTS.md 写成 README 复制品**。占了上下文，却没提供 agent 真正需要的可执行信息。
7. **忽略嵌套与作用域**。多包仓库里，根目录与子目录的约定可能冲突；多数工具支持就近覆盖，但语义并不完全一致，需实测。
