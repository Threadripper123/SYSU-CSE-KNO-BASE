# 03 推理性能优化技术栈全景

> 主题库：vLLM 与 AI Infra　｜　源文件：（纯文本条目）　｜　3,049 字符　｜　14 个片段　｜　更新于 2026-11-13
推理优化的所有手段，最终都落在两个瓶颈上：**decode 是 memory-bound（搬权重和 KV），prefill 是 compute-bound（算 GEMM）**。判断一个优化在解决哪个瓶颈，比记住术语更重要。

## 一、调度层：把 GPU 喂饱
### 1. 连续批处理（Continuous Batching / iteration-level scheduling）
- 问题：静态 batch 要等最慢的请求结束才能换批，GPU 空转。
- 做法：以 iteration 为粒度，每步结束后把完成的请求踢出、把新请求插进来。
- 来源：Orca（OSDI'22）提出，vLLM/TensorRT-LLM/SGLang 全部采用。
- 代价：调度器复杂度上升，需要每步重建 batch 元数据（CPU 开销）。

### 2. Chunked Prefill
- 问题：一个 32K 的 prefill 会独占 GPU 数十毫秒，期间所有 decode 请求卡住，ITL 抖动。
- 做法：把长 prefill 切成固定大小（如 2048 token）的 chunk，与 decode 混在同一批里。
- 收益：ITL 更平滑，GPU 利用率更高。
- 代价：prefill 总时间略增（多次 kernel launch），TTFT 可能变差。

### 3. 优先级与抢占
- 多租户/在线服务需要 SLO 分级：短请求优先、长请求限流、超时抢占。
- vLLM 支持 priority 与 preemption；被抢占请求重算（见 02）。

## 二、显存层：让 batch 更大
| 手段 | 原理 | 收益 | 代价 |
|---|---|---|---|
| PagedAttention | 分块分配，消除预留浪费 | 并发提升 2–4× | kernel 复杂 |
| 前缀缓存 | 复用相同前缀的 KV | 多轮/模板场景 TTFT 大幅下降 | 低命中率时反而降并发 |
| KV 量化（FP8/FP4） | KV 以低精度存储 | KV 显存减半/减至 1/4 | 精度损失，需校准 |
| KV offload | 冷 KV 放 CPU/SSD | 支持超长上下文 | PCIe 带宽成为瓶颈 |
| GQA/MQA（模型侧） | 减少 KV 头数 | KV 显存降 4–8× | 需改模型结构 |

## 三、计算层：让每个 token 更便宜
### 1. 算子融合与专用 attention
- FlashAttention：tiling + online softmax，避免把 N×N 注意力矩阵写回 HBM，显存 O(N) 而非 O(N²)。
- FlashInfer：面向 serving 的 attention kernel 库，覆盖 paged KV、cascade、投机解码等形态。
- 融合 MLP/归一化：减少 kernel launch 与中间张量读写。

### 2. 量化
- **W8A8（FP8）**：Hopper/Blackwell 原生支持，权重与激活都量化，GEMM 直接吃 FP8 Tensor Core。
- **W4A16（AWQ/GPTQ）**：只量化权重，decode 时省带宽（decode 就是搬权重），是单卡跑大模型最实用的方案。
- **FP4/NVFP4**：Blackwell 代际的进一步压缩，KV cache 与权重都可用。
- 详见 08。

### 3. 投机解码（Speculative Decoding）
- 用小模型/ngram/EAGLE 头先猜 k 个 token，大模型一次前向并行验证，接受则一次出多个 token。
- 收益取决于**接受率**；对高确定性任务（代码、格式化输出、RAG 摘抄）收益大，对开放式创作收益小甚至负收益。
- 代价：额外显存（draft 模型）、额外算力；batch 很大时 decoder 已接近 compute-bound，收益下降。
- vLLM 支持 draft model、ngram、EAGLE、MLP speculator 等多种后端。

### 4. CUDA Graph / 图捕获
- decode 每步结构固定，用 CUDA Graph 捕获后重放，消掉 Python 与 kernel launch 开销。
- 限制：形状必须固定，遇到 batch 变化要重新捕获或使用 padding（vLLM 用不同 batch size 的多份 graph）。

## 四、并行层：多卡怎么切
| 方式 | 切什么 | 通信量 | 适用 |
|---|---|---|---|
| Tensor Parallel（TP） | 单层内按头/维度切 | 每层两次 all-reduce，量大 | 单机 NVLink，最常用 |
| Pipeline Parallel（PP） | 按层切 | 只传激活，量小 | 跨机、层数多 |
| Data Parallel（DP） | 复制模型，切请求 | 几乎无 | 吞吐扩展，副本间负载均衡 |
| Expert Parallel（EP） | MoE 专家分散到卡 | all-to-all，量最大 | MoE 模型 |

TP 的通信发生在每层，必须有 NVLink/高速互联；跨机 TP 基本不可行，应改 PP 或 PD 分离。

## 五、架构层：PD 分离
- 把 prefill 与 decode 放到不同实例：prefill 池吃长 prompt（compute-bound），decode 池保持大 batch（memory-bound）。
- KV 需要在两池之间传输：NIXL、LMCache、vLLM 的 KV connector / production-stack。
- 收益：两类负载互不干扰，各自选最优并行策略与硬件配比。
- 代价：KV 传输延迟与带宽、系统复杂度、故障面变大。
- 适用：大规模在线服务、prompt 长且波动大；小规模部署通常不划算。

## 六、框架层面能改什么
- **vLLM**：生态最广、OpenAI 兼容最好、V1 后调度开销低；MoE/量化/多模态支持全。
- **SGLang**：RadixAttention 前缀树 + 前端 DSL，多轮对话与结构化生成（约束解码）场景强。
- **TensorRT-LLM**：编译期图优化 + 手写 kernel，单机极限性能通常最好，但模型适配成本高。
- **LMDeploy / MLC-LLM**：分别在国产卡适配与端侧/异构上有优势。

## 优化顺序建议（实战）
1. 先量：TTFT、ITL、吞吐（req/s、output tok/s）、GPU 利用率、KV 使用率。
2. 若 KV 使用率高、并发上不去 → 先做前缀缓存 / KV 量化 / 调 block_size。
3. 若 GPU 利用率低、batch 小 → 查调度与 CPU 开销（是否被 Python 卡住）。
4. 若单请求就慢 → 看 attention 实现与量化，而非调度。
5. 若多卡扩展比差 → 看 TP 通信是否跨机、是否该用 PP/PD 分离。
