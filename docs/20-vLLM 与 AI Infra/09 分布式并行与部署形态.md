## 四种并行，切的东西完全不同
| 方式 | 切分对象 | 通信模式 | 通信量 | 典型场景 |
|---|---|---|---|---|
| TP（张量并行） | 单层内的权重矩阵 | 每层 2 次 all-reduce | 大（与激活同量级） | 单机多卡，NVLink |
| PP（流水并行） | 按层切分 | 只传层间激活 | 小 | 跨机、超深层 |
| DP（数据并行） | 复制模型，切请求 | 基本无 | 极小 | 多副本扩吞吐 |
| EP（专家并行） | MoE 的专家分散 | all-to-all | 最大 | 大 MoE 模型 |

### TP 的细节
Megatron 式做法：注意力的 QKV 按 head 切（列并行），输出投影按行切（行并行），FFN 的第一个矩阵列并行、第二个行并行。这样每层前后各一次 all-reduce，通信可以与前后的计算部分重叠。
- 单机 NVLink（H100 约 900GB/s）下 TP=8 通常效率不错；
- 跨机走 IB/RoCE（数百 Gb/s）时，TP 的 all-reduce 会成为瓶颈，应改 PP 或减少 TP 度。

### PP 的细节
- 微批（micro-batch）流水，1F1B 调度减少气泡；气泡比例约 (p−1)/(m+p−1)，p 为 stage 数、m 为微批数。
- 推理场景 PP 的气泡比训练小（decode 是逐步的，天然流水），但 TTFT 会因跨 stage 传递而增加。
- vLLM 支持 PP（部分后端为实验性），Ascend 版本文档对 PP 的配置有详细说明。

### DP 与负载均衡
- 每个副本独立调度，请求分发靠前置负载均衡（K8s Service / 网关 / vLLM 的 DP 模式）。
- 坑：请求长度分布不均时，各副本的 KV 压力差异大，需要按队列长度或 KV 使用率做路由，而不是简单轮询。

### EP 与 MoE
- 专家分散到不同卡，每个 token 经 all-to-all 送到对应专家，再送回。
- 通信量与专家并行度、top-k 成正比，是 MoE 推理的主要瓶颈；常见优化是分组 GEMM、通信计算重叠、专家复制（redundant experts）。

## PD 分离（Prefill-Decode Disaggregation）
### 动机
prefill 与 decode 的资源画像相反：prefill 吃算力、decode 吃带宽与显存。混部时两者互相干扰，且难以分别扩缩容。

### 架构
1. 请求先进 prefill 实例，算完 KV。
2. KV 通过高速链路传给 decode 实例（NIXL / LMCache / vLLM KV connector）。
3. decode 实例长期持有 KV 并持续出 token。

### 收益与代价
- 收益：TTFT 与 ITL 解耦、各自最优并行策略、按负载分别扩容、长 prompt 不再拖累 decode 池。
- 代价：KV 传输（几十 MB 到 GB 级）、额外一跳网络延迟、系统复杂度与故障面、需要 KV-aware 路由。
- 结论：**只有在规模足够大、prompt 长度波动明显时才有正收益**；小规模部署通常不如混部。

## 主流框架对比
| 框架 | 强项 | 弱项 |
|---|---|---|
| vLLM | 生态最广、OpenAI 兼容好、功能全（量化/MoE/多模态/PD） | 极限性能略逊于编译型方案 |
| SGLang | RadixAttention 前缀树、结构化输出（约束解码）、前端 DSL | 生态与算子覆盖略窄 |
| TensorRT-LLM | 编译期图优化 + 手写 kernel，单机极限性能强 | 模型适配成本高、迭代慢 |
| LMDeploy | 国产卡（昇腾等）适配、TurboMind 引擎 | 社区规模较小 |
| DeepSpeed-FastGen / MII | 与训练栈打通 | 推理生态不如前两者 |

## 部署实践清单
1. **先定 SLO**：TTFT、ITL、可用性，再反推并行策略与硬件配比。
2. **单卡先跑满**：把 batch、KV 利用率、前缀缓存调好，再上多卡——很多「需要多卡」其实是调度没调好。
3. **TP 度尽量 ≤ 单机卡数**，优先 NVLink 域内。
4. **监控 KV 使用率**而不是 GPU 利用率：KV 满了才是真正的瓶颈信号。
5. **自动扩缩容看队列长度 + KV 使用率**，不要只看 QPS。
6. **灰度与回滚**：换量化/换后端要能按比例切流。
7. **压测用真实长度分布**，不要用固定 128 token 的合成流量。

## 容量估算（快速版）
- 单副本并发 ≈ 可用 KV 显存 / (平均上下文 token × 单 token KV 字节)。
- 需要副本数 ≈ 峰值并发 / 单副本并发（再乘 1.2–1.5 的冗余）。
- 权重显存 = 参数量 × dtype 字节 / TP 度（每卡）。
- 网络：TP 的 all-reduce 带宽需求 ≈ 2 × 激活字节 × 层数 / 单步时间，跨机时必须核算。
