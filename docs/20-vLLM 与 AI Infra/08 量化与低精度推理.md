# 08 量化与低精度推理

> 主题库：vLLM 与 AI Infra　｜　源文件：（纯文本条目）　｜　2,456 字符　｜　11 个片段　｜　更新于 2026-11-13
## 为什么量化对推理几乎总是划算
- **decode 是带宽瓶颈**：每生成一个 token 要把全部权重读一遍。7B FP16 = 14GB，H100 3.35TB/s → 单请求理论上限约 240 tok/s。换成 W4（约 3.5GB）理论上是 4 倍。
- **prefill 是算力瓶颈**：量化收益主要来自 FP8 Tensor Core 的 2× 算力，而不是带宽。
- **KV cache 量化直接换并发**：KV 减半，并发就能接近翻倍，长上下文场景收益最大。

## 数值格式速查
| 格式 | 位宽 | 动态范围 | 精度 | 用途 |
|---|---|---|---|---|
| FP16 | 16 | ±65504 | 10 位尾数 | 通用，易溢出 |
| BF16 | 16 | 同 FP32 指数 | 7 位尾数 | 训练/推理默认，稳定 |
| FP8 E4M3 | 8 | ±448 | 3 位尾数 | 权重与激活（Hopper+） |
| FP8 E5M2 | 8 | ±57344 | 2 位尾数 | 梯度，推理少用 |
| INT8 | 8 | 对称 ±127 | 均匀 | W8A8，需 scale |
| INT4 | 4 | ±7 | 均匀 | W4A16 权重only |
| NVFP4 / MXFP4 | 4 | e2m1（±6） | 2 位尾数 | 每 16/32 元素一个 scale，Blackwell 主打 |

FP4 的关键不是位宽而是**分块缩放**：每 16 个元素共享一个 FP8 scale，避免整层一个 scale 导致的精度崩塌。

## 三条主流路线
### 1. W8A8（FP8 / SmoothQuant / INT8）
- 权重和激活都量化，GEMM 直接用低精度 Tensor Core，prefill 与 decode 都受益。
- 难点是**激活离群值**：某些通道数值极大，直接量化会毁精度。SmoothQuant 把激活的量化难度按通道转移到权重上（数学上等价变换）。
- FP8 在 Hopper 上几乎是「免费加速」，精度损失通常 <0.5% 且无需校准数据（用 weight-only scale + 动态激活 scale）。

### 2. W4A16（GPTQ / AWQ）
- 只量化权重，激活保持 FP16。decode 时带宽省 4 倍，但要做反量化，kernel 开销不可忽略。
- **GPTQ**：逐层用二阶信息（Hessian 近似）补偿量化误差，需要校准集。
- **AWQ**：观察到约 1% 的显著通道决定精度，按激活幅度做 per-channel 缩放保护它们，不需要反向传播，鲁棒性好。
- 实测：7B/70B 上 W4 相对 FP16 的困惑度损失通常在 0.1–0.3 之间，任务指标基本持平；但代码/数学类任务对量化更敏感。

### 3. KV Cache 量化
- FP8 KV：per-head 或 per-token scale，显存减半，长上下文吞吐提升明显。
- NVFP4 KV：Blackwell 上进一步压到 1/4，需要 per-block scale 与更多校准。
- 风险：KV 误差会随上下文长度累积，长上下文召回类任务要单独评测；attention 的 softmax 会放大 logits 误差。

## vLLM 中的实际配置
- 量化后端通过 quantization 参数选择：fp8、awq、gptq、int8、gguf、nvfp4 等（具体支持随版本变化，见 vLLM 量化文档）。
- KV cache 精度：kv_cache_dtype（如 fp8、fp8_e5m2），与权重量化解耦。
- 注意：量化 kernel 是否可用依赖 GPU 架构（FP8 需 Hopper+，FP4 需 Blackwell），不支持的组合会回退到慢路径甚至启动失败。

## 性能预期（务必实测）
| 场景 | 理论收益 | 实测常见 |
|---|---|---|
| decode，W4A16 vs FP16 | 4× 带宽 | 2–3×（反量化与 kernel 效率损失） |
| decode，FP8 vs FP16 | 2× 带宽 | 1.5–1.9× |
| prefill，FP8 vs BF16 | 2× 算力 | 1.3–1.8× |
| 并发，FP8 KV | 2× KV 容量 | 接近 2×（受其他开销摊薄） |

batch 越大，decode 越接近 compute-bound，权重量化的收益越小；此时 FP8 激活量化与 KV 量化更值钱。

## 常见坑
1. **只看困惑度**：长上下文、代码、多语言任务的退化往往在 PPL 上看不出来。
2. **scale 布局不对**：per-tensor 在 LLM 上几乎必然掉点，至少 per-channel（权重）+ per-token（激活）。
3. **与 TP 的交互**：按通道量化时，切分维度决定 scale 是否需要跨卡同步。
4. **校准集偏差**：用通用语料校准，在领域数据上可能明显退化。
5. **反量化开销**：W4 的小 batch decode 可能被反量化指令拖慢，反而不如 FP8。
6. **不要混用未验证组合**：量化权重 + FP8 KV + 投机解码，误差会叠加。

## 决策建议
- 单卡部署大模型、显存吃紧 → W4A16（AWQ 优先，免校准调参）。
- Hopper/Blackwell 上追求吞吐 → FP8 W8A8 + FP8 KV。
- 长上下文服务 → 优先 KV 量化，再考虑权重量化。
- 精度敏感（医疗、法律、代码）→ 只做 FP8，且必须过任务级评测。
